# 020.5 SPDX 软件物料清单与签名绑定

状态：本机生成、标准工具校验、签名绑定和解压验证通过；生产供应商/命名空间、许可证复核和制品平台展示待配置。

## 目标与实现

使用仓库本地 .NET Tool Manifest 固定 Microsoft.Sbom.DotNetTool 4.1.5，不依赖开发机全局安装或可移动 latest。`New-ServerRelease.ps1` 当前要求调用者明确提供不含冒号/换行的组织名称和绝对 HTTPS Namespace Base，工具按 SPDX 生成 `Organization: <名称>`，防止正式包默默使用虚构生产身份。CI 只使用保留域 `example.invalid` 和 `ET CI Test`，明确不是正式发行身份。验证端同时要求预期组织名称与 namespace，不能仅因包内字段格式正确就信任攻击者自报身份。

发布构建完成 Bin/Config 后，工具只扫描 `DotNet` 服务端组件路径，不把 Unity 客户端 npm 包误列为服务器依赖；生成 SPDX 2.2 到 `_manifest/spdx_2.2`，禁用符号链接跟随和在线 ClearlyDefined 许可证补全，启用本地包元数据解析。随后立即调用微软工具 Validate，要求至少一个包、69 个运行文件全部存在且哈希一致；失败、无包或验证报告异常都阻止打包。

ET 自有 `release-manifest.json` 移到 `_manifest/et`，避免被 SPDX 当作额外运行文件。它列出并哈希 SPDX JSON 与其 SHA 文件；外部 RSA-PSS attestation 又绑定 release manifest 哈希和整个 ZIP，因此 SBOM、二进制、配置、版本与源提交处于同一签名信任链。验证器在验签和 manifest 校验后检查 SPDX-2.2、CC0-1.0 dataLicense、产品名/版本、HTTPS namespace 末尾的源提交+版本，并明确要求 MongoDB.Driver 2.30.0、SharpCompress 0.50.4、Snappier 1.3.1，拒绝 EPPlus 重新出现。

参考实现与格式边界来自 [Microsoft SBOM Tool 官方仓库](https://github.com/microsoft/sbom-tool)；当前官方工具支持 SPDX 2.2/3.0，本项目先固定 2.2 以保持现有验证链稳定，格式升级另建记录。

## 上线边界

SBOM 是组件与文件清单，不证明组件无漏洞、许可证允许商业发行或构建主机可信；漏洞仍由 020.2 扫描，来源/签名由 020.4 验证。当前包元数据显示部分组件的 concluded license 为 NOASSERTION，必须由发行主体在商业发布前完成许可证/NOTICE 人工审查，不能把 `-pm true` 当法律结论。

正式版本必须改用真实公司/个人 Supplier 与受控 HTTPS namespace，并在不可变制品库展示/保留 SBOM。Microsoft SBOM 工具本身也是构建供应链依赖：虽固定版本并由 NuGet 恢复，仍需纳入工具更新、漏洞监控和来源审计。未实现 VEX、许可证策略阻断或 SPDX 签名目录的第三方透明日志。

## 回滚

新格式验证器只对显式测试开关兼容旧包；生产不应因 SBOM 生成失败降级为无 SBOM 发布。若工具故障，应停止发布并从固定工具/缓存恢复，不手工伪造清单。该项只改变构建产物，未部署、未修改数据库和运行中服务器。
