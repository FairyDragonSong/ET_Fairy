# 商业上线后续路线图

## 定位

第一阶段 001–013 已完成代码层面的登录、认证、持久化、基础运维和安全补充。本路线图用于补齐真实生产环境验证、渠道认证、账号运营、高可用、监控、商业数据和发布安全能力。

当前结论：第一阶段适合作为预发布验证基线，但在 014、016、018、020 的上线范围验收通过前，不能认定为足以承载商业项目正式上线。微信小游戏作为首发渠道时，015 同样属于上线硬门禁；需要多节点或滚动发布时，017 也属于上线硬门禁。

## 优先级定义

| 优先级 | 含义 |
| --- | --- |
| P0 上线硬门禁 | 对当前正式上线范围不可缺少；未验收不得上线 |
| P0 规模化上线必需 | 单节点小规模试运行可以暂缓，但多节点、滚动发布或容灾上线前必须完成 |
| P1 按业务启用 | 对应业务功能启用前必须完成，不要求一次实现所有游戏业务 |

## 固定实施顺序

### 当前项目范围补充（2026-09-12）

用户确认以单机玩法为主、目标 2000 人在线。优先补齐 014 容量验收、016 账号治理、018 告警和 020 发布恢复；015 在微信渠道接入前完成，017 按多实例部署需要推进，019 按实际经济/奖励业务拆分。编号保留用于追溯，不代表必须提前实现所有候选业务。

容量测试目标与验证边界见 [014.2-单机玩法容量验收](014.2-单机玩法容量验收.md)。当前仍只有本机测试证据，不作生产容量承诺。

### 014 预发布环境与第一阶段实测验收

目标：在接近生产的真实环境中证明 001–013 不只是能够编译，而是能够承受故障并恢复。

范围：

- 使用启用认证、TLS、`retryWrites` 的 MongoDB Replica Set，不使用开发单机配置。
- 验证账号与角色事务提交、主动回滚、唯一索引和历史脏数据审计。
- 验证 MongoDB 主节点切换、短时断网、进程崩溃、重启恢复和优雅停机。
- 验证登录、重复登录、普通地图重连、房间重连、Gate Key 重放与过期。
- 执行备份并在隔离数据库完成恢复演练，核对账号、角色及关键字段。
- 进行基线压测，记录登录吞吐、在线量、消息延迟、错误率、CPU、内存和数据库连接数。

完成标准：所有 P0 场景有可重复脚本、时间戳结果和故障证据；不存在数据重复、孤儿角色、旧 Session 越权或未解释的数据丢失；容量结论包含安全余量。真实环境不可用时只能标记“受阻”或“部分验证”，不能标记完成。

### 015 微信小游戏登录与账号绑定

目标：以服务端可信方式支持微信小游戏 Code 登录，同时保留现有账号密码用于内部试用或迁移。

范围：

- 客户端只提交一次性 Code，服务端向微信接口换取身份；AppSecret 仅保存在服务端 Secret 中。
- 建立平台身份模型，使用 `Provider + OpenId` 唯一约束；按业务需要保存 UnionId，禁止把昵称当作身份。
- 处理 Code 一次性消费、超时、重试、微信接口限流、熔断和错误码映射。
- 定义游客、密码账号与微信身份的绑定、冲突、换绑和迁移规则，防止账号被覆盖或合并错误。
- 登录传输使用真实 WSS/TLS 终止链路，并验证代理转发配置和证书更新。
- 使用微信测试环境或可控桩覆盖成功、失效 Code、重复 Code、接口超时和身份冲突。

完成标准：客户端无法伪造 OpenId；同一微信身份不能创建重复账号；Code 不可重放；Secret 不进入日志、仓库或客户端；绑定操作可审计且失败时不产生半绑定数据。

### 016 商业账号生命周期与管理审计

目标：补齐上线后处理封禁、凭据变更、会话撤销和客服操作所需的账号治理能力。

范围：

- 封禁、解封、强制下线、注销/软删除和账号状态机。
- 密码修改与重置；当前阶段不具备可信找回渠道时，不开放自助找回。
- 会话与设备记录、登录时间、来源摘要、刷新/撤销策略及全端失效。
- 管理后台或管理命令采用独立身份、最小权限、二次确认和不可抵赖审计。
- 敏感操作限流、告警；日志仅保留必要的主体、动作、结果和关联 ID。
- 明确数据保留、导出和删除策略，并按目标发行地区完成隐私与未成年人合规评审。

完成标准：账号状态在所有登录入口一致生效；封禁和强退在约定时限内生效；权限越权测试失败；每次管理操作可追溯且审计记录不能由普通运营角色修改。

### 017 分布式部署、高可用与故障治理

目标：让 Realm、Gate、Map 等服务从单实例正确性升级到多实例和故障切换正确性。

范围：

- 明确各服务的无状态/有状态边界、服务发现、路由注册和摘除规则。
- 将登录限流、一次性凭据、会话归属等跨节点状态放入具备原子语义的共享协调层，或证明粘性路由边界可靠。
- 外部请求和跨服务命令定义超时、有限重试、退避、熔断、幂等键和重复消息处理规则。
- 验证实例崩溃、网络分区、延迟、乱序、MongoDB 切主和部分服务不可用。
- 支持滚动发布、连接排空、版本兼容窗口与自动回滚。

完成标准：多实例下不能绕过限流或重复消费凭据；关键写入重试不产生重复资产；单实例故障不会扩大为全服故障；滚动升级期间达到约定可用性目标。

### 018 监控告警与容量治理

目标：从“能查看健康状态”升级为“故障能被及时发现、定位和处置”。

范围：

- 建立登录成功率、鉴权失败、在线数、断线重连、消息延迟、队列/邮箱积压、异常率和数据库指标。
- 指标标签控制基数，不包含账号、角色名、IP、Token 等敏感或高基数字段。
- 建立日志集中检索、关联 ID、保留周期和访问权限。
- 按服务定义 SLI/SLO、分级告警、值班通知、抑制与恢复通知。
- 编写登录失败、数据库故障、内存增长、消息积压和容量不足 Runbook。
- 使用压测结果设定资源水位、扩容阈值与容量预算。

完成标准：关键故障能在目标时间内告警；告警包含可执行 Runbook；演练能由指标和日志定位根因；无敏感信息泄漏和不可控标签基数。

### 019 商业数据系统与运营安全基线

目标：为真正涉及价值的数据建立强一致、幂等和可审计的业务底座。具体模块按游戏设计逐项拆分，不能用一份大提交一次完成。

候选子项：

- 背包、货币、道具流水与不可变账本；所有增减带业务原因和幂等键。
- 订单、支付回调、发货、补单、退款和对账；支付能力启用前需单独安全评审。
- 邮件、附件领取、礼包码、任务奖励及防重复领取。
- 配置版本、热更新灰度、活动开关、补偿工具和操作审计。
- 客服查询、数据修复和运营后台 RBAC；高风险操作双人复核。
- 反作弊、风控信号、举报与处罚闭环，按玩法风险逐步扩展。

完成标准：每个价值变更可追溯、可对账且幂等；重复请求和消息重投不会重复发放；修复工具不直接绕过账本；各子项分别建档、测试和提交。

### 020 发布、安全与灾难恢复工程

目标：建立可重复、可审计、可回滚的商业发布流程，并证明灾难后能恢复服务和数据。

范围：

- CI 执行编译、测试、依赖与凭据扫描，产物带版本、校验和及来源记录。
- 配置与 Secret 分离，权限最小化，支持轮换、吊销和泄漏应急。
- 网络分区、管理端口隔离、防火墙、入口防护、DDoS 方案和 TLS 配置基线。
- 灰度/金丝雀发布、数据库迁移前向兼容、自动回滚和紧急停服开关。
- 定义 RPO/RTO、备份保留和跨故障域策略，定期完成隔离恢复演练。
- 上线检查表、变更审批、发布记录、事故分级、响应流程和复盘模板。
- 上线前执行依赖漏洞扫描、权限审计、渗透测试和故障演练并闭环高风险问题。

完成标准：相同版本可由流水线重复部署；失败发布能在目标时间回滚；Secret 可无停机或按预案轮换；恢复演练达到 RPO/RTO；未关闭的高风险安全问题阻断发布。

## 上线门禁矩阵

| 上线形态 | 必须完成 |
| --- | --- |
| 内部开发与功能联调 | 001–013；仅允许开发配置和测试数据 |
| 受控预发布/删档测试 | 014、016、018，并完成 020 中适用于测试环境的发布、备份和应急项 |
| 微信小游戏商业首发 | 014–016、018、020；启用多实例或滚动发布时还必须完成 017 |
| 含充值、付费道具或运营发奖 | 上一行全部，加上 019 中对应的支付、账本、发货、对账和运营权限子项 |
| 多区服或规模化运营 | 014–020 全部完成，并基于压测和 SLO 给出容量与容灾结论 |

## 每项实施纪律

1. 开始升级时，从[升级记录模板](升级记录模板.md)创建对应编号文档，并在总索引将状态改为“实施中”。
2. 实现、配置、迁移脚本、自动化验证、运行结果、遗留风险和回滚方案同步写入记录。
3. 只完成本地编译或模拟测试不能替代真实依赖环境验收；验证边界必须明确记录。
4. 每项升级完成后单独创建 Git 提交，不混入其他升级或用户未授权的改动。
5. 若一个编号内容过大，实施时拆成 `019.1` 等可独立验证的子项，并分别建档和提交。
6. 上线结论按本路线图的门禁矩阵判断，不以“功能代码已存在”代替生产验收。
