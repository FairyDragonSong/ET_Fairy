# 020.11 不可变签名发布槽位

状态：本机安装、复验、重复拒绝和磁盘篡改拒绝通过；生产目录 ACL、磁盘与服务监督器待目标主机验收。

## 目标与边界

把 020.9 的签名 ZIP 转换为服务器上可启动、可复验、不会被下一次发布覆盖的版本槽位。槽位 ID 固定为 `<SemVer>-<ZIP SHA-256 前12位>`；同一目标已存在时拒绝覆盖，回滚始终引用原槽位，不在服务器现场拼接 DLL。

本项完成安装和完整性验证，不切换当前运行版本、不停止进程，也不声明文件系统在管理员面前不可修改。“不可变”表示部署工具没有覆盖路径且任何变化会被逐文件复验发现；生产仍需只读 ACL、磁盘保护和监督器每次启动前强制调用验证器。

## 槽位结构

部署根必须是仓库外、非盘符根目录，并通过 `ConfirmDeploymentRoot` 精确二次确认：

```text
<DeploymentRoot>/
  releases/
    <version>-<archive-hash-prefix>/
      evidence/          原始 ZIP、校验和、attestation JSON 和 RSA-PSS 签名
      package/           解压后的 Bin、Config、SPDX 和签名绑定 manifest
      slot-metadata.json 安装时间、版本、提交、完整 ZIP 哈希和槽位 ID
```

`Install-ServerReleaseSlot.ps1` 先通过 `Test-ServerRelease.ps1` 验证受信公钥、Key ID、SBOM 身份、签名、干净来源、ZIP/manifest 及全部文件；复制证据后再次计算 ZIP 哈希，防止验证和复制之间被替换。内容先进入同一 `releases` 目录下的随机 staging，完整复验通过后才移动为最终槽位。

正式安装默认要求 `WorktreeDirty=false`。`-AllowDirtyTestArtifact` 仅用于自动化测试，不得出现在生产部署命令中。

## 槽位复验

`Test-InstalledServerSlot.ps1` 每次执行都会：

- 重新验证 evidence 中唯一发布包的外部签名、SBOM 和归档内容；
- 由版本和完整归档哈希重新推导槽位 ID，并核对目录名与 metadata；
- 将已安装 manifest 的 SHA-256 与已签名 attestation 精确比较；
- 拒绝不安全/重复相对路径、缺失文件和额外文件；
- 对 package 中每个文件重新核对字节数和 SHA-256。

因此只替换 DLL、配置、SBOM、manifest、metadata 或 evidence 任一处都不能同时绕过外部信任链。验证器需要的公钥本身仍必须由受保护信任存储提供，不能从槽位内自报。

## 验证记录

- `Test-ServerRollout.ps1 -AllowDirtyTestArtifacts` 已扩展真实槽位测试：构建并签名候选包，安装到专用仓库外临时 DeploymentRoot，安装后完整复验通过，槽位归档哈希与灰度计划候选哈希一致。
- 对相同版本和哈希再次安装被拒绝，证明工具不覆盖已有槽位。
- 打开已安装 `package/Bin/Hotfix.dll` 并修改首字节后，槽位复验失败；没有把“原 ZIP 仍有效”误当成“解压运行文件仍有效”。
- 原 020.9 的双向兼容、双人/监控密钥隔离、PROMOTE/HOLD/ROLLBACK、计划篡改和版本倒序测试继续全部通过。
- 自动化 finally 对 `et-rollout-test-<GUID>` 路径和值进行检查后删除整个专用临时目录，私钥、槽位和篡改副本残留均为 0。

## 安全、兼容和回滚

安装是无运行时副作用的准备操作：不修改数据库、不改端口、不停止进程、不修改当前版本指针。安装失败只清理工具本次创建且名称满足 `.staging-<GUID>` 的目录，不删除已存在槽位或其他发布数据。

回滚时必须先复验目标旧槽位，并核对其版本、提交和完整 ZIP 哈希与 020.9 双签计划的 Current 一致。020.9 已阻止旧版本无法读取候选数据库 Target 的发布，因此槽位可用不代表可以绕过兼容门禁。

槽位目录若允许服务进程或普通运维账号写入，攻击者可在两次验证之间修改文件。生产应让安装身份拥有写权限、运行身份只读，并由监督器在创建进程前最后一次复验；更强场景应使用只读镜像/制品挂载和应用白名单。
