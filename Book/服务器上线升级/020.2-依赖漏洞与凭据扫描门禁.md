# 020.2 依赖漏洞与凭据扫描门禁

状态：当前服务端依赖与新增提交门禁本机验证通过；历史潜在凭据处置、远端 CI 首跑和定期复扫仍待完成。

## 目标与实现

- `Test-DependencyVulnerabilities.ps1` 使用 .NET/NuGet 官方审计输出检查顶级及传递依赖。无法查询、JSON 格式异常或存在任意已知漏洞均失败，不因严重性较低而放行。
- GitHub 工作流在恢复后执行该门禁；依赖使用九份 `packages.lock.json` 锁定，CI 使用 `--locked-mode`，依赖声明和锁文件不一致即失败。
- CI 从 Gitleaks 官方 release 下载 8.30.1 Windows x64 包，校验仓库固定 SHA-256 后，只扫描本次 push 的提交范围或 PR 变更范围；输出 100% 脱敏。checkout 使用完整历史以解析范围，不保留凭据。
- 初次创建分支或手动运行因没有可靠的远端前序提交，只扫描当前提交。定期全历史扫描与旧问题处置另行执行，不把不可信范围默认为安全。

## 漏洞修复

2026-09-12 初始审计发现：MongoDB.Driver 2.17.1 的 High；EPPlus 5.8.8 传递引入 System.Drawing.Common 5.0.0 Critical、System.Formats.Asn1 5.0.0 High 和 SharpCompress 0.30.1 Moderate。升级 MongoDB.Driver 到 2.30.0、SharpZipLib 到 1.4.2；移除服务端源码未引用的 EPPlus。MongoDB.Driver.Core 2.30.0 仍声明过低的 SharpCompress/Snappier 下限，因此显式锁到 SharpCompress 0.50.4 和 Snappier 1.3.1，以覆盖 2026 年目录穿越和畸形 Snappy 数据无限循环公告。移除 NU1903 抑制，未来高危恢复警告不再被项目隐藏。

MongoDB 驱动升级后真实测试先暴露两处 `ObjectSerializer` 兼容错误：消息日志以 object 名义类型序列化，Unit 跨地图传输也以 object 序列化。修复为消息按具体类型格式化；普通 BSON 值按具体类型序列化；Entity 传输仍以抽象 Entity 为名义类型保留鉴别器。没有把新驱动的全局 ObjectSerializer 类型限制放宽。

参考：[MongoDB.Driver 公告 GHSA-7j9m-j397-g4wx](https://github.com/advisories/GHSA-7j9m-j397-g4wx)、[SharpCompress 公告 GHSA-6c8g-7p36-r338](https://github.com/advisories/GHSA-6c8g-7p36-r338)、[Snappier 公告 GHSA-pggp-6c3x-2xmx](https://github.com/advisories/GHSA-pggp-6c3x-2xmx)。公告与本机 NuGet 源均在验证日重新查询。

## 历史风险与上线门禁

全历史扫描 3127 个提交、约 337.69MB，在已从当前树删除的 `Unity/Assets/Plugins/ShareSDK/ShareSDKDevInfo.cs` 历史版本中发现 55 条潜在 API Key/Secret（首次出现提交 e47fb8cd84766c95b54b286db4b761413e7574f9）。未在文档或输出中记录密钥值，也未建立忽略规则。仓库拥有者必须在对应 ShareSDK/渠道平台识别、吊销并轮换全部仍有效凭据；若仓库曾向不可信主体开放，应按已经泄漏处理。只删除当前文件或重写 Git 历史都不能代替服务端吊销。

本轮没有渠道账号权限，无法证明这些历史值已失效，因此 020 安全门禁仍未完成。后续需要保存平台侧吊销记录（不含 Secret）、评估是否清理远端历史，并建立全历史定期复扫。生产 Secret 必须来自独立密钥系统，不写仓库、构建参数或制品。

## 回滚

代码回滚会恢复已知漏洞和运行时旧行为，不建议用于生产。若新驱动出现未覆盖兼容问题，应先停发，在受控分支回退依赖与 BSON 修改并重跑旧驱动的全套测试；不对数据库做降级迁移。本轮未修改业务数据结构，失败短跑只产生独立测试账号、角色、会话及失败证据，由现有验收数据保留策略保存。
