# 020.16 跨故障域备份库存与保留门禁

状态：离线规则通过且本机单盘实测正确拒绝；生产跨域存储待接入。

## 目标

020.14 证明单份备份可验签和安全恢复，020.15 证明一次恢复满足 RTO；仍不能证明最新备份满足 RPO、存在多个故障域副本或保留历史足够。本项把存储提供方的库存观察与双人审批组合成三方签名证据，并对上述条件失败关闭。

## 实现

- `New-BackupStorageInventory.ps1` 重新验证 020.15 双签策略和 020.14 最新签名备份。
- 最新备份的创建时间到库存观察时间不得超过策略 RPO。
- 商业最低值固定为至少 2 个唯一存储位置、2 个不同故障域、7 天 Compliance 对象锁、7 个日恢复点、4 个周恢复点和 3 个月恢复点；实际库存可以签署更高要求。
- 每个最新备份副本必须绑定同一 Manifest SHA-256，声明静态加密及非空 EncryptionKeyId，使用 `Compliance` 锁，并达到签署的不可变期限。
- 存储观察、库存请求、库存批准、备份签名和演练观察五个密钥按公钥指纹强制隔离。
- 库存 JSON 由存储观察者、请求人和批准人三方 RSA-PSS/SHA-256 签名且不可覆盖。
- `Test-BackupStorageInventory.ps1` 每次重新验证全部签名、策略、真实备份内容、RPO、副本、故障域、加密、对象锁和日/周/月覆盖。

## 自动化验证

`Test-BackupStorageGovernance.ps1` 使用七把临时 RSA-3072 密钥通过：三签库存、RPO 新鲜度、两个故障域、加密和 Compliance 锁、日周月保留。以下场景均被拒绝：两个副本处于同一故障域、副本未加密、日保留点不足、最新备份超过 RPO、库存内容被篡改。CI 已加入该门禁。

提交后针对真实 `ET_LOCAL_ACCEPTANCE` 新生成签名备份 `ET_LOCAL_ACCEPTANCE-20260912T1224580576399Z`（Manifest SHA-256 `1aa1fc3e57781d5c8fbf415915f55df6e48d4b3cd72561437a72da182dfb9745`）。库存只报告本机 `D:` 上一个 `local-machine` 故障域，要求仍为至少 2 份/2 域；门禁以 `Backup copy count is below policy` 正确拒绝，未生成通过库存。脱敏输入保存在 `D:\Program Files\ET\_Env\mongo-local\evidence\local-storage-inventory`。

该失败是正确验收结果，不能用两个目录名伪装成跨域成功；因此 020.16 代码门禁完成，但生产跨域事实仍未达标。

## 信任边界

Copies 和 Retention 输入是存储观察身份对云存储 API/备份平台结果的证明；仓库脚本无法自行确认一个字符串是否真在另一机房。生产必须由只读存储审计服务生成输入，保护观察私钥，并保留提供方对象版本、对象锁和 KMS 审计日志。人工编写后签名只证明签名者作出声明，不证明基础设施事实。

本机 `D:` 单磁盘的多个文件夹属于同一故障域，不满足生产要求。签名不提供加密，真正的副本仍必须由存储平台实施静态和传输加密。

## 回滚

库存未达标时阻断上线或升级，不删除现有备份。修复方式是创建真实独立域副本、补齐保留点后生成新的 InventoryId；不得降低要求、复用签名、改写旧库存或把同盘路径声明成不同区域。
