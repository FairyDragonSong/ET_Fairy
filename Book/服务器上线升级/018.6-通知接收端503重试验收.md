# 018.6 通知接收端 503 重试验收

状态：2026-09-12 本机 503 重试验收与正常通知模式回归均通过，完整 018 仍实施中。

## 场景

`Test-LocalMetrics.ps1 -NotificationRetry` 自动启用本机 Prometheus/Alertmanager 测试。接收端仅在该模式下首次收到已通过鉴权的 et-primary firing 通知时，保存拒绝证据并返回真实 HTTP 503；不把拒绝尝试写入成功接收记录。后续请求恢复正常处理。

测试不是调用通知 API 手动重发：仍由真实目标停止触发 Prometheus，再由 Alertmanager 自身重试投递。只有收到同一 fingerprint 的 firing 且接收时间晚于拒绝时间才允许测试继续重启目标，然后继续验证同一告警的 resolved 通知。

`rejected-alert.json` 保存 503 状态、测试 job、fingerprint 和拒绝时间；`received-alerts.jsonl` 保存成功接收与恢复的精简记录。两种证据分开，不能用“接收端看到了请求”代替“成功接收了通知”。不记录认证头、token 或原始载荷。

## 结果

带故障注入的最终脚本检查 16 项 PASS，新增 `alertmanager-retries-same-alert-after-receiver-503`，同时保留鉴权拒绝、规则触发/恢复、双进程隔离和端口释放检查。报告增加 `LocalNotificationRetryVerified`，其他模式为 false。

正常 `-Alertmanager` 模式的 15 项检查亦回归通过。故障样本中同一 fingerprint 的成功 firing 接收时间比 503 拒绝晚约 506.26ms；这是本机单次观察，不是重试时延 SLO。两次运行的临时 token 已清理。本轮未改动服务器业务代码，不新增业务功能验收结论。

证据在本机 `_Env/metrics-test-<随机ID>/`，result.json 含父提交和工作区标记。临时组件与 token 按既有 finally 清理；不修改真实业务数据或发送外部消息。

## 尚未覆盖

本项只证明一次 503 后恢复接收时的重试，不代表接收进程长时间离线、DNS/TLS 错误、响应丢失后的重复通知、Alertmanager 强杀恢复或外部通知供应商限流已经验收。HTTP 2xx 也不能证明某个值班人已阅读通知。

告警重复抑制、通知接收幂等策略、常驻部署和正式渠道/接收人仍待完成。测试接收端不是生产网关；异常注入通过测试子进程的环境变量开启，不新增服务器业务开关。

回滚这组测试即可；没有数据库迁移、永久监听或生产通知配置变化。
