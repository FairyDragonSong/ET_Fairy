# 017 分布式部署、高可用与故障治理

状态：实施中；017.1–017.3 本机完成，真实多主机与故障切换未验收。

## 当前部署边界

当前首发以单机玩法、单区服为主。Release 拓扑已经包含两个 Gate、两个 Map，但 Realm 的登录限流和 Location 路由表仍是进程内状态。因此增加 Realm 或 Location 进程并不会自动得到高可用，反而可能绕过登录限流或产生分裂路由。

本项不提前引入 Redis、Kubernetes 或未经容量证明的自动重试。先把现有架构能够安全支持的拓扑写成可执行门禁，再按真实部署规模逐项替换有状态边界。

## 017.1 部署拓扑静态门禁

新增 `Tools/ServerOps/Test-ServerTopology.ps1`，对发布使用的四类 StartConfig JSON 执行以下检查：

- Machine、Process、Scene、Zone 标识唯一，所有引用必须存在；
- 同一机器的进程监听端口和 Scene 对外端口不得冲突；
- 同一区服的 Scene 名称唯一，Realm 和 Gate 必须配置客户端端口；
- 游戏区必须至少有一个 Gate 和 Map；
- 在共享原子登录准入实现前，每个游戏区只允许一个 Realm；
- 在共享或具备一致性切换的 Location 实现前，全拓扑只允许一个 Location。

多个 Gate 和 Map 保持允许：一次性 Gate Key 由 Realm 定向请求目标 Gate 签发并只在该 Gate 消费；Unit/Player 使用 Location 地址间接寻址。该结论只说明现有正常路径，不等于 Gate、Map、Location 已通过跨主机故障切换。

`Test-ServerTopologyPolicy.ps1` 覆盖安全样例、多 Realm、重复监听、缺失 Location，并验证仓库 Release 拓扑。CI 在服务器基线中执行该测试，避免不安全拓扑进入发布包。

## 验证结果

- 2026-09-13：离线策略测试通过，Release 拓扑为 1 Realm、2 Gate、2 Map、1 Location。
- 本项不声称完成多实例限流、Location 高可用、网络分区、MongoDB 切主、滚动版本兼容或跨主机排空。

## 部署与回滚

部署前对实际导出的 `Config/Json/s/StartConfig/<环境>` 执行门禁。失败时应修正配置或先实现相应共享协调能力，不得删除检查来强行扩容。回滚本提交只移除发布前检查，不改变运行时数据；但会重新允许不安全拓扑被误发布。
