# 018.22 生产告警路由与凭据隔离门禁

状态：配置生成、amtool schema/路由验证和 CI 门禁完成；真实外部渠道、接收人和送达演练待验收。

## 目标

本机 Alertmanager 测试只能证明 webhook 收发能力，不能直接成为生产配置。本项增加仓库外配置生成器，强制 critical 与 warning 的通知地址和凭据隔离、HTTPS、恢复通知、分组、抑制和未知等级升级，避免明文地址、共享 Token 或未分类告警静默丢弃。

## 配置契约

`New-ProductionAlertmanagerConfiguration.ps1` 从两份仓库外 Secret 文件读取不同的绝对 HTTPS webhook，避免含签名路径的 URL 出现在命令历史或进程参数中，并拒绝 HTTP、userinfo、query 和 fragment；两份 Bearer Token 同样必须位于仓库外、为普通非重解析文件、长度 32–4096 字节且内容不同。Token 内容不会写入配置或命令输出，Alertmanager 仅通过 `credentials_file` 读取。

配置文件只能创建在仓库外，拒绝覆盖已有文件及路径重解析点。生成结果包含配置路径和 SHA-256，不包含 URL、Token 或认证头。Alertmanager schema 必须在配置中保存实际 webhook，因此生成文件本身也属于受限 Secret 制品，必须纳入 020.20 ACL 和变更审批。

路由策略：

- critical 使用独立 `critical-oncall`，重复间隔 30 分钟；
- warning 使用独立 `warning-oncall`，重复间隔 4 小时；
- 未知或缺失 severity 默认进入 critical，不允许静默丢弃；
- 两类接收均强制 `send_resolved=true`、禁止 HTTP redirect，单批最多 20 条；
- critical 会抑制同一 alertname/stage/component/deployment 的 warning，避免同一根因重复轰炸；
- 分组标签全部来自固定运维维度，不加入账号、角色、IP 或 Token。

## 自动化验证

`Test-ProductionAlertmanagerGovernance.ps1` 使用本机固定 Alertmanager 0.34.0：

- `amtool check-config` 验证生成配置 schema；
- `amtool config routes test` 验证 critical、warning 和未知等级分别落到预期接收端；
- 验证两端都启用恢复通知且配置未嵌入 Token；
- 拒绝 HTTP、共享接收地址、共享凭据和覆盖已有配置；
- GitHub Windows CI 安装已校验 SHA-256 的相同 Alertmanager 版本并执行相同门禁。

本机全部检查通过。测试使用 `example.invalid` 和随机临时 Token，没有向外部人员发送消息。

## 生产边界

正式部署仍需：由值班负责人提供两组真实渠道及仓库外 Secret；以生产服务身份验证 Token ACL；对配置制品审批和签名；常驻/高可用 Alertmanager 部署；执行 critical、warning、重复抑制、接收端 429/5xx、长时离线、恢复通知和人员确认演练。只有 HTTP 2xx 不能证明人员已阅读。

如生产平台只有一个 webhook，也不能通过复用本项两组参数伪造职责隔离，应在通知网关内部建立独立升级策略并提供可审计证据。

## 回滚

保留上一份已验证配置并通过受控 reload/服务切换回滚；不要覆盖生成文件。回滚时验证 Alertmanager 配置状态、两级路由和测试告警恢复通知，Token 不自动撤销，泄漏时必须在接收平台单独吊销。
