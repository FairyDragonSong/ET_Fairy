# 018.5 本机告警与恢复通知闭环

状态：2026-09-12 本机通知送达、同一告警恢复关联和未授权接收拒绝验收通过；完整 018 未完成。

## 工具与链路

`Install-LocalAlertmanager.ps1` 固定安装官方 Alertmanager 0.34.0 Windows amd64，SHA256 `0e4b832325d6d9b737b3255a242da7b11cb7a641d7f81f7e2aabe34b3207cd79`。来源：[官方发布页](https://prometheus.io/download/)、[官方通知配置文档](https://prometheus.io/docs/alerting/latest/configuration/)。安装在 `_Env/alertmanager-0.34.0`，包含 amtool，安装不会启用常驻服务。

运行 `Test-LocalMetrics.ps1 -Alertmanager`（自动包含 -Prometheus）建立本机链路：ET 进程 → Prometheus → Alertmanager → 带独立随机凭据的测试 webhook 接收端。

Prometheus 使用 30909；Alertmanager 只监听 127.0.0.1:30910，并通过空 `--cluster.listen-address` 禁用集群监听；测试接收端只监听 127.0.0.1:30911。全部临时进程均隐藏启动，仅操作脚本创建的进程。

Alertmanager 使用 1 秒分组等待/间隔与 send_resolved，阈值仅用于本机演练。webhook Bearer token 存放在本轮受 ACL 保护的目录，配置只引用文件路径，不写入 Git 或结果报告。

## 验收内容

- amtool 配置校验和 promtool 配置/规则校验通过。
- 双目标正常采集后，未授权 POST 接收端返回 401。
- 停止主目标，Prometheus 检测离线并进入 firing，接收端实际收到 et-primary firing 通知后才允许重启目标。
- 重启后规则恢复，接收端实际收到 resolved；要求 fingerprint 与之前 firing 相同且接收时间顺序正确。
- 验证 Alertmanager 与接收端实际监听为回环，保留全部双进程、采集凭据及旧入口隔离测试。

`received-alerts.jsonl` 只保留 Status、Job、Alertname、Fingerprint、ReceivedAtUtc，不保留原始 HTTP 请求、Authorization 或完整告警载荷。接收端只识别本项测试告警和两个固定 job，不转发通知，不执行收到的任何内容。

## 边界与证据

报告保存在 `_Env/metrics-test-<随机ID>/result.json`，另有查询时间戳和 received-alerts.jsonl。测试结束回收 App、Prometheus、Alertmanager、接收端进程并删除三份临时 token，保留证据和测试数据库。

本轮最终复跑共 15 项检查 PASS，报告 LocalNotificationVerified=true；received-alerts.jsonl 保留 et-primary 的 firing 与 resolved 接收记录，同一 fingerprint 和时间顺序断言通过。最终核查 App/Prometheus/Alertmanager 已退出，三份 token 文件均不存在。本轮仅变更工具与验收脚本，不新增服务器业务测试结论。

该接收脚本是本机测试工具，不是生产 webhook 网关；没有全面恶意请求、慢连接或重放防护验收。Alertmanager 管理 API 目前只用回环隔离，未配置额外身份认证或 TLS，不得直接代理到公网。

本项证明本机真实通知投递与恢复通知，并不证明用户收到了企业微信/邮件/短信。常驻服务、持久凭据管理、外部通知渠道/值班人、生产阈值、抑制/去重/重试、通知端中断恢复、多机器和平台高可用仍待完成。临时进程通过精确进程对象结束，未证明通知队列强停恢复。

无业务数据库迁移或用户消息发送。回滚脚本可停止使用本功能，不自动删除已安装工具或证据。
