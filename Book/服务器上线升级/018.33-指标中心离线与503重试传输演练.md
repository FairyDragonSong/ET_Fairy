# 018.33 指标中心离线与 503 重试传输演练

状态：本机非回环 TLS 真实 remote_write 离线恢复与 503 重试通过；进程强杀零丢失、双主机及生产中心仍未证明。

## 目标

018.30 已证明逐主机 relay 配置可被 Prometheus 解析，但没有发出真实 remote_write 请求。本项验证本机抓取与中心连接相互隔离，以及中心短时离线和返回 HTTP 503 时 Prometheus 能否在进程持续运行期间恢复发送。

## 演练流程

`Test-ProductionMetricsRelayTransport.ps1`：

1. 在回环地址启动一个只接受独立 bearer token 的最小 Prometheus 指标源；
2. 为本机非回环 IPv4 生成临时 CA/TLS 证书，使用 018.30 生成器创建生产形态配置并通过 promtool；
3. 中心监听器保持离线 8 秒，确认 Prometheus 未退出、本机鉴权抓取至少持续两轮且 TSDB WAL 已生成；
4. 启动复用 018.32 的两请求 TLS 接收端，第一次 remote_write 返回 503，第二次返回 200；
5. 验证两次请求路径均为 `/api/v1/write`、请求体 SHA-256 相同、采用 Snappy protobuf 且 bearer Authorization 存在；
6. 停止全部拥有的子进程并删除本轮临时证书、token、WAL 和接收记录。

测试不解析或保存 bearer 值，只记录认证头是否存在；接收端不写生产数据库。

## 验证

2026-09-13 最终通过结果：

- Prometheus 3.13.3、非回环地址 `192.168.1.8`；
- 本机受认证抓取在中心离线时继续运行，WAL 文件存在；
- 首次中心响应 503，随后自动重试并收到 200；
- 两次 Snappy protobuf body 哈希一致，证明是同批请求重试；
- 报告明确 `PrometheusRestarted=false`、`CrashReplayGuaranteed=false`、`CrossHostVerified=false`；
- 测试门禁加入 Windows CI。

开发过程中曾尝试把“强杀 Prometheus 后补发未确认样本”作为通过条件。3.13.3 重启日志显示 `Replaying WAL`，但多轮 30 秒观察均未向接收端发送崩溃前的小批量样本；因此删除了这一不可靠断言，并把它记录为明确风险，而不是通过增加等待时间制造偶然成功。最初一次脚本错误遗留的测试临时目录已在核对进程和绝对路径后删除。

## 边界与后续

Prometheus 官方说明 remote_write 在运行期间从 WAL 读取、对失败重试，但中心持续不可用超过 WAL 保留窗口后未发送数据会丢失，见 [Remote write tuning](https://prometheus.io/docs/practices/remote_write/)。本项只证明存活进程的短时离线和 503 恢复，不承诺强杀、断电或磁盘损坏时零丢失。

生产需要按可接受丢失窗口选择：受监督的单 relay 加告警，或两个独立 relay 配合中心去重/HA。选择依赖实际中心平台能力，不能在当前仓库替用户假定。最终还要在两台生产等价主机上验证网络分区、凭据轮换、磁盘水位和中心查询结果。

回滚只删除测试与 CI 项，不改变 018.30 生产配置；生产环境禁止使用测试证书、指标源或接收端。
