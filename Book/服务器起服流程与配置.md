# 服务器起服流程与配置

本文记录 YIUI/ET 服务器从配置生成、编译到启动的完整流程，并说明 `Machine`、`Process`、`SceneType`、`Fiber`、`Zone` 之间的关系。

## 一、整体流程

服务器起服可以概括为：

```text
修改 StartConfig Excel
        ↓
使用 Luban 生成 .bytes 和 .json
        ↓
编译 ET.sln，生成 Bin/App.dll 等程序集
        ↓
选择 StartConfig，并启动 Server 或 Watcher
        ↓
服务器读取配置
        ↓
按 Process 创建当前进程负责的 Fiber/Scene
        ↓
Realm、Gate、Map、Router 等服务开始监听
```

配置决定“启动哪些服务以及部署在哪里”，代码决定“这些服务启动后执行什么业务”。

## 二、环境和目录

服务器项目目标框架为 `.NET 8`，启动前需要安装对应的 .NET SDK。

常用目录：

```text
DotNet/                         .NET 服务端工程
Bin/                            编译输出及服务器工作目录
Config/Excel/s/                 服务端运行时读取的二进制配置
Config/Json/s/                  便于人工检查的 JSON 配置
Unity/Assets/Config/Excel/      Luban Excel 配置源文件
Unity/Assets/Config/Excel/StartConfig/
                                各套起服配置源文件
Logs/                           服务器日志
Tools/Luban/GenConfig.bat       Windows 配置生成脚本
```

服务器必须以 `Bin` 为工作目录启动。服务端配置加载器使用如下相对路径：

```text
../Config/Excel/s/...
```

如果从项目根目录或其他目录直接运行 `App.dll`，可能出现配置文件找不到的问题。

## 三、起服配置集

起服配置源文件位于：

```text
Unity/Assets/Config/Excel/StartConfig/
```

当前项目包含：

| 配置集 | 用途 |
| --- | --- |
| `Localhost` | 本机开发、局域网联调 |
| `Release` | 发布及多进程部署 |
| `Benchmark` | 压力测试 |
| `RouterTest` | Router 专项测试 |

命令行通过 `--StartConfig` 选择配置集，例如：

```text
--StartConfig=StartConfig/Localhost
```

`StartConfig` 目录中每套环境都包含四张核心表：

```text
StartMachineConfig.xlsx
StartProcessConfig.xlsx
StartSceneConfig.xlsx
StartZoneConfig.xlsx
```

### 3.1 StartMachineConfig

描述参与部署的物理机、虚拟机或云主机。

| 字段 | 含义 |
| --- | --- |
| `Id` | 机器编号 |
| `InnerIP` | 服务器内部通信地址 |
| `OuterIP` | 客户端能够访问的对外地址 |
| `WatcherPort` | Watcher 端口 |

本机开发示例：

```json
{
  "Id": 1,
  "InnerIP": "127.0.0.1",
  "OuterIP": "192.168.1.7",
  "WatcherPort": "10000"
}
```

注意事项：

- 纯本机客户端可以把 `OuterIP` 配置为 `127.0.0.1`。
- Android 真机或局域网内其他设备不能使用电脑的 `127.0.0.1`，应配置电脑局域网 IP。
- 云服务器通常使用内网 IP 进行服务间通信，使用公网 IP、域名或负载均衡地址对外提供服务。
- 修改 IP 后还应同步检查防火墙、安全组、端口映射和客户端入口地址。

### 3.2 StartProcessConfig

描述要启动的操作系统进程。

| 字段 | 含义 |
| --- | --- |
| `Id` | 进程编号，对应命令行的 `--Process` |
| `MachineId` | 该进程部署在哪台机器上 |
| `Port` | 进程间内部通信端口 |

示例：

```json
{
  "Id": 1,
  "MachineId": 1,
  "Port": 20001
}
```

`MachineId` 必须能在 `StartMachineConfig` 中找到对应机器。`Port` 不为 `0` 时，进程启动阶段会创建 `NetInner` Fiber，供跨进程 Actor 消息使用。

### 3.3 StartSceneConfig

描述服务器中实际运行的逻辑服务。每一行通常对应一个启动时创建的 Fiber，其根实体是一个 Scene。

| 字段 | 含义 |
| --- | --- |
| `Id` | Scene 对应的 FiberId，必须唯一 |
| `Process` | 该 Scene 由哪个进程承载 |
| `Zone` | 所属逻辑业务区或数据区 |
| `SceneType` | Scene 的业务类型 |
| `Name` | Scene 实例名称 |
| `Port` | 对外监听端口；不需要监听时可为 `0` |

示例：

```json
{
  "Id": 2,
  "Process": 1,
  "Zone": 1,
  "SceneType": "Gate",
  "Name": "Gate1",
  "Port": 30003
}
```

含义是：在 1 号进程中创建一个 FiberId 为 2、属于 Zone 1 的 Gate，实例名为 `Gate1`，监听 30003 端口。

常见 `SceneType`：

| SceneType | 职责 |
| --- | --- |
| `Realm` | 登录及区服入口 |
| `Gate` | 客户端网关和会话管理 |
| `Location` | Actor 位置服务 |
| `Match` | 匹配服务 |
| `Map` | 地图及游戏逻辑 |
| `RouterManager` | Router 管理及地址分配 |
| `Router` | 网络路由和转发 |

### 3.4 StartZoneConfig

描述逻辑业务分区以及该分区使用的数据库。

| 字段 | 含义 |
| --- | --- |
| `Id` | Zone 编号 |
| `DBConnection` | MongoDB 连接地址 |
| `DBName` | 数据库名 |
| `Desc` | 分区说明 |

示例：

```json
{
  "Id": 1,
  "DBConnection": "mongodb://127.0.0.1",
  "DBName": "ET1",
  "Desc": "游戏区"
}
```

需要持久化数据的 Zone 必须配置有效的数据库连接。Router 等基础设施 Zone 如果不访问数据库，可以不填写数据库信息。

## 四、Process、Fiber、SceneType 与 Zone

这些概念属于不同维度：

| 概念 | 回答的问题 |
| --- | --- |
| `Machine` | 服务部署在哪台主机？ |
| `Process` | 服务运行在哪个操作系统进程？ |
| `FiberId` | 当前进程中具体是哪一个执行和隔离单元？ |
| `SceneType` | 这个 Fiber 承担什么业务职责？ |
| `Zone` | 这个 Fiber 服务于哪个逻辑业务区或数据区？ |
| `Name` | 这个具体实例叫什么？ |

### 4.1 SceneType 与 Fiber

服务器根据 `StartSceneConfig` 创建 Fiber：

```csharp
await FiberManager.Instance.Create(
    SchedulerType.ThreadPool,
    startConfig.Id,
    startConfig.Zone,
    startConfig.Type,
    startConfig.Name);
```

创建完成后，框架根据 `SceneType` 分发对应的 `FiberInit`，因此 `SceneType` 决定该 Fiber 初始化哪些组件、注册哪些业务能力。

### 4.2 Zone 与 Fiber

`Zone` 是保存在 Fiber 上的逻辑上下文：

```csharp
public int Id;
public int Zone;
```

Fiber 中的 Entity 可以通过 `entity.Zone()` 获取所属 Zone。Zone 常用于：

- 按区选择数据库；
- 查找当前区的 Gate、Map 等 Scene；
- 隔离不同游戏区的数据和业务关系；
- 让同一套代码、同一个进程承载多个逻辑区。

Zone 不是进程、线程、FiberId，也不是 Actor 地址的一部分。Actor 的唯一寻址主要由 `Process + FiberId + InstanceId` 构成，Zone 负责业务归属而不是唯一寻址。

以本地配置为例，同一个进程可以同时承载多个 Zone：

```text
Process 1
├── Zone 1：游戏区
│   ├── Realm
│   ├── Gate1、Gate2
│   ├── Location
│   ├── Match
│   └── Map1、Map2
└── Zone 3：路由区
    ├── RouterManager
    └── Router01～Router04
```

因此：

- 一个 Process 可以包含多个 Zone；
- 一个 Zone 可以包含多个不同 `SceneType`；
- 多个 Fiber 可以属于同一个 Zone；
- 同一种 `SceneType` 也可以在不同 Zone 中各自部署。

一句话概括：`SceneType` 决定 Fiber 做什么，`Zone` 决定 Fiber 为哪个逻辑区服务。

## 五、修改和生成配置

### 5.1 修改配置源文件

应修改：

```text
Unity/Assets/Config/Excel/StartConfig/配置集/*.xlsx
```

不要直接修改：

```text
Config/Excel/**/*.bytes
Config/Json/**/*.json
Unity/Assets/Scripts/Model/Generate/**
```

这些都是生成结果，下次执行 Luban 时会被覆盖。

### 5.2 生成配置

Windows 下执行：

```powershell
Set-Location "项目根目录\Tools\Luban"
.\GenConfig.bat
```

也可以在 Unity 中打开：

```text
ET → Build Tool → ExcelExporter
```

生成后的主要目录：

| 目录 | 用途 |
| --- | --- |
| `Config/Excel/c` | 客户端二进制配置 |
| `Config/Excel/s` | 服务端二进制配置 |
| `Config/Excel/cs` | 客户端、服务端共享配置 |
| `Config/Json/*` | 供开发人员核对的可读配置 |

服务端运行时读取的是 `.bytes`，不是 JSON。修改 Excel 后只改 JSON 或只看 JSON，不代表运行配置已经生效。

配置生成后建议先检查对应 JSON，例如：

```text
Config/Json/s/StartConfig/Localhost/
```

重点检查：

- ID 是否重复；
- `MachineId` 是否存在；
- `Process` 是否存在；
- `Zone` 是否存在；
- IP、数据库地址和端口是否正确；
- 同一台机器上的监听端口是否冲突。

如果只修改配置数据且没有修改表结构，重新生成配置并重启服务器即可。修改表结构或生成代码后，需要重新编译服务端。

## 六、编译服务器

在 Rider 中编译整个 `ET.sln`，或者在项目根目录执行：

```powershell
dotnet build .\ET.sln
```

主要输出位于：

```text
Bin/App.dll
Bin/Model.dll
Bin/Hotfix.dll
Bin/Loader.dll
```

服务器启动时会动态加载 `Hotfix.dll` 和对应 PDB，因此编译后应确认这些文件完整存在。

## 七、本地单进程起服

### 7.1 Unity 启动

停止 Unity Play，然后打开：

```text
ET → ServerTools
```

选择 `Localhost`，点击：

```text
Start Server(Single Process)
```

该按钮本质上执行：

```powershell
dotnet App.dll --Process=1 --StartConfig=StartConfig/Localhost --Console=1
```

### 7.2 PowerShell 启动

```powershell
Set-Location "项目根目录\Bin"

dotnet .\App.dll `
  --AppType=Server `
  --Process=1 `
  --StartConfig=StartConfig/Localhost `
  --Develop=1 `
  --Console=1
```

也可以直接运行 `App.exe`：

```powershell
.\App.exe --Process=1 --StartConfig=StartConfig/Localhost --Console=1
```

常用参数：

| 参数 | 说明 | 默认值 |
| --- | --- | --- |
| `--AppType` | `Server`、`Watcher` 等程序类型 | `Server` |
| `--StartConfig` | 起服配置集 | `StartConfig/Localhost` |
| `--Process` | 当前进程编号 | `1` |
| `--Develop` | `0` 正式、`1` 开发、`2` 压测 | `0` |
| `--LogLevel` | 日志等级 | `0` |
| `--Console` | 是否创建服务器控制台组件 | `0` |

当前 `ServerTools` 窗口虽然提供“正式/开发/压测”选择，但启动命令没有传递 `--Develop`，因此该选择暂时不会生效。需要该参数时应使用命令行，或者补充编辑器启动代码。

## 八、Watcher 多进程起服

当一套配置包含多个 `StartProcessConfig` 时，可以在每台服务器上启动一个 Watcher：

```powershell
Set-Location "项目根目录\Bin"

dotnet .\App.dll `
  --AppType=Watcher `
  --StartConfig=StartConfig/Release `
  --Develop=0 `
  --Console=1
```

Watcher 的处理过程：

1. 获取本机所有 IP；
2. 遍历 `StartProcessConfig`；
3. 通过 `MachineId` 找到进程所属机器及其 `InnerIP`；
4. 选择 `InnerIP` 与本机匹配的进程；
5. 为每个匹配进程执行一次 `dotnet App.dll --AppType=Server --Process=...`。

因此多机部署时，每台机器的 `InnerIP` 必须配置正确，否则 Watcher 可能找不到本机配置，或者不会启动预期进程。

也可以绕过 Watcher，手动分别启动：

```powershell
dotnet .\App.dll --Process=1 --StartConfig=StartConfig/Release --Console=1
dotnet .\App.dll --Process=2 --StartConfig=StartConfig/Release --Console=1
```

每个 `--Process` 必须在 `StartProcessConfig` 中存在。

## 九、服务器内部启动顺序

内部调用链如下：

```text
DotNet.App.Program.Main
        ↓
Init.Start 解析 Options，初始化日志、TimeInfo、FiberManager
        ↓
CodeLoader 加载 Model 和 Hotfix 程序集
        ↓
Entry.Start 初始化框架单例并加载配置
        ↓
创建 Main Fiber
        ↓
EntryEvent2_InitServer 根据 AppType 分支
        ↓
Server：读取当前 StartProcessConfig
        ↓
按需创建 NetInner Fiber
        ↓
查找 StartSceneConfig 中 Process 等于当前进程的记录
        ↓
逐个创建 Realm、Gate、Map、Router 等 Fiber
```

服务器只创建 `StartSceneConfig.Process == Options.Process` 的 Scene。因此修改 Scene 所属进程后，需要确认目标进程确实已经启动。

## 十、启动后的验证

建议依次检查：

1. 服务端控制台没有异常退出；
2. `Logs` 目录没有新的 Error 日志；
3. MongoDB 已启动，数据库连接地址正确；
4. 配置中所有监听端口没有被占用；
5. `StartMachineConfig` 的内外网 IP 符合当前环境；
6. 防火墙或云安全组已经放行客户端需要访问的端口；
7. RouterManager、Router、Realm、Gate 等必要 Scene 均已创建；
8. 客户端入口地址与服务端的对外地址一致。

Windows 下可以检查端口：

```powershell
Get-NetTCPConnection -State Listen |
  Sort-Object LocalPort |
  Format-Table LocalAddress,LocalPort,OwningProcess
```

UDP 端口可以使用：

```powershell
Get-NetUDPEndpoint |
  Sort-Object LocalPort |
  Format-Table LocalAddress,LocalPort,OwningProcess
```

## 十一、常见问题

### 11.1 找不到配置文件

检查启动工作目录是否为 `Bin`，并确认对应文件存在：

```text
Config/Excel/s/StartConfig/配置集/*.bytes
```

### 11.2 找不到 Process 配置

命令行的 `--Process` 必须对应 `StartProcessConfig.Id`。

### 11.3 Watcher 没有启动任何进程

检查 `StartMachineConfig.InnerIP` 是否与当前机器的实际 IP 匹配，并检查各进程的 `MachineId`。

### 11.4 MongoDB 连接失败

检查 MongoDB 是否启动、端口是否正确，以及当前 Scene 的 `Zone` 对应的 `StartZoneConfig` 是否填写了 `DBConnection` 和 `DBName`。

### 11.5 客户端连接不上

重点检查：

- 客户端是否错误使用了 `127.0.0.1`；
- `OuterIP` 是否为客户端可达地址；
- RouterManager、Router、Realm、Gate 端口是否启动；
- Windows 防火墙、云安全组和 NAT 映射是否放行；
- 修改 Excel 后是否重新生成 `.bytes` 并重启服务器。

Android 真机联调的详细步骤参见同目录下的《安卓真机连接本地服务器指南》。

### 11.6 修改配置后没有生效

确认执行顺序完整：

```text
修改 Excel → 运行 GenConfig.bat → 检查生成 JSON/.bytes → 重启服务器
```

不要直接修改生成的 JSON，因为服务器实际读取的是 `.bytes`。

## 十二、发布提示

项目根目录提供 `Publish-linux-x64.ps1`，会执行 Linux x64 发布并把 `Bin`、`Config` 复制到发布目录。发布前仍需确认：

- `Release` 中的 IP、端口和数据库连接不是本地占位值；
- 目标机器已安装匹配的 .NET Runtime，因为当前脚本使用 `--no-self-contained`；
- 配置目录与程序目录的相对关系保持不变；
- 日志目录具有写权限；
- 防火墙、安全组、反向代理或端口映射已经配置；
- 密码、数据库凭据等敏感信息没有提交到公开仓库。

生产环境推荐由 systemd、容器平台或其他进程管理工具托管服务端进程，并配置自动重启、日志轮转和监控告警。
