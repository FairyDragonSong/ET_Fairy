# 微信小游戏适配与构建指南

本文记录 YIUI 从常规 Unity 客户端适配到微信小游戏的改动、完整构建流程、服务器 WebSocket 配置，以及本次联调中遇到的典型问题。

> 本文目标平台是“微信小游戏”，不是普通微信小程序。文中为了方便，部分地方简称“小游戏”。

## 一、当前适配结果

目前已经验证通过以下流程：

- Unity 工程可以切换到 `MiniGame` 目标并完成微信小游戏转换。
- 小游戏可以启动 ET 主 Fiber。
- HybridCLR 热更新程序集和 AOT 补充元数据可以正常加载。
- YooAsset 可以用 `WebPlayMode` 初始化并加载远端资源。
- 小游戏可以进入登录界面。
- 客户端可以通过 HTTP 获取 Router 列表。
- 客户端可以通过 WebSocket 连接 ET Router，并完成登录联调。

本机微信开发者工具联调示例：

```text
资源服务器：http://127.0.0.1:8080
RouterManager：http://127.0.0.1:30300/get_router
Router WebSocket：ws://RouterIP:(Router端口+1000)/et/
```

`127.0.0.1` 只适用于服务器与微信开发者工具运行在同一台电脑上；真机不能用它访问电脑。局域网明文 HTTP/WS 只用于开发调试，正式真机环境必须改成微信后台配置过的合法域名，并使用 HTTPS/WSS。

## 二、为什么原工程不能直接运行

微信小游戏运行环境本质上接近 WebGL，和 Windows、Android 等平台存在几个关键差异：

1. 不支持 ET 原有的托管线程和线程池调度方式。
2. 不能直接使用普通 UDP/TCP Socket 连接游戏服务器。
3. `HttpClient` 在小游戏运行环境中不可直接照搬桌面端用法。
4. YooAsset 需要使用适合 WebGL/小游戏的 `WebPlayMode`。
5. IL2CPP + HybridCLR 对泛型异步状态机的裁剪更严格。
6. 微信对资源下载域名、HTTPS/WSS 和网络权限有额外限制。
7. 导出前必须保证热更新 DLL、AOT DLL、YooAsset 产物和小游戏目标一致。

本次适配围绕以上问题完成。

## 三、代码适配内容

### 3.1 主线程 Fiber 调度

涉及文件：

```text
Unity/Assets/Scripts/Core/Fiber/Fiber.cs
Unity/Assets/Scripts/Core/World/Module/Fiber/FiberManager.cs
```

ET 原本会根据 Fiber 类型使用主线程、独立线程或线程池调度器。但是微信小游戏/WebGL 没有可供 ET 正常使用的托管后台线程。

当前处理方式是：

- `Main` Fiber 继续使用主线程调度器。
- 在 `UNITY_WEBGL`、`UNITY_WEIXINMINIGAME` 或 `TUANJIE_WEIXINMINIGAME` 下：
  - `Thread` 调度器映射到主线程调度器。
  - `ThreadPool` 调度器也映射到主线程调度器。
- FiberManager 释放调度器时进行去重，避免同一个主线程调度器被重复释放。
- Unity 平台日志宏改为 `UNITY_5_3_OR_NEWER`，覆盖小游戏编译目标。

这解决了小游戏启动时无法创建后台调度线程、Main Fiber 初始化失败的问题。

注意：这是一种单线程兼容方案。原来放在线程或线程池 Fiber 中的重计算任务，在小游戏中实际仍会占用主线程，后续需要关注单帧耗时。

### 3.2 IL2CPP/HybridCLR 泛型异步状态机

涉及文件：

```text
Unity/Assets/Scripts/Core/World/Module/EventSystem/EventSystem.cs
Unity/Assets/Scripts/Core/World/Module/EventSystem/IEvent.cs
```

小游戏启动时曾出现：

```text
MissingMethodException:
ET.EventSystem+<PublishAsync>d__...::.ctor
```

继续修复后还出现：

```text
AEvent<Scene, EntryEvent1>+<Handle>d__...::.ctor
```

原因是 `PublishAsync<S,T>` 和 `AEvent<S,A>.Handle` 都生成了泛型 async 状态机。IL2CPP 与 HybridCLR 组合构建时，这些具体泛型状态机的构造方法可能没有正确保留，最终在热更新代码调用时找不到方法。

当前处理方式是：

- 泛型 `PublishAsync<S,T>` 本身不再声明为 `async`。
- 泛型 `AEvent<S,A>.Handle` 本身不再声明为 `async`。
- 泛型方法只负责收集或转发 `ETTask`。
- 实际等待逻辑转移到非泛型异步辅助方法中。

这样避免运行时依赖被裁剪的泛型 async 状态机构造方法。

下文是当时的解释：
之前出现这个问题，核心不是事件逻辑写错，而是“泛型 async 方法跨越 HybridCLR 热更新程序集和 IL2CPP AOT 程序集”导致的代码生成缺失。
具体发生了什么
修改前的方法是：
public async ETTask PublishAsync<S, T>(S scene, T a)
{
    // ...
    await ETTaskHelper.WaitAll(list);
}
以及：
public async ETTask Handle(S scene, A a)
{
    await Run(scene, a);
}
C# 编译器看到 async 后，不会把它编译成普通方法，而是生成隐藏的异步状态机。例如：
EventSystem.<PublishAsync>d__4<S, T>
AEvent<S, A>.<Handle>d__3
内部逻辑大致相当于：
var stateMachine = new <PublishAsync>d__4<Scene, EntryEvent1>();
stateMachine.scene = scene;
stateMachine.a = eventData;
stateMachine.MoveNext();
因此运行时除了需要 PublishAsync<Scene, EntryEvent1>，还需要隐藏状态机的具体实例：
<PublishAsync>d__4<Scene, EntryEvent1>::.ctor
为什么小游戏才报错
调用链是：
Hotfix FiberInit_Main
    ↓
AOT EventSystem.PublishAsync<Scene, EntryEvent1>
    ↓
创建泛型 async 状态机
    ↓
找不到具体状态机构造方法
小游戏使用 IL2CPP，代码需要在构建时提前编译为 Wasm，不能像 Unity Editor 的 Mono/JIT 那样，在运行时临时生成新的泛型实例。
而这里的具体泛型组合：
Scene + EntryEvent1
Scene + EntryEvent2
Scene + EntryEvent3
主要由热更新程序集发起调用。IL2CPP 构建 AOT 程序集时，未必能够完整分析热更新程序集未来会用到哪些泛型 async 状态机，于是没有生成对应的 Wasm/native 实现。
运行到：
await EventSystem.Instance.PublishAsync(root, new EntryEvent1());
HybridCLR 能找到 PublishAsync 方法，但进入方法准备创建状态机时，发现：
<PublishAsync>d__...<Scene, EntryEvent1>::.ctor
没有对应的 AOT 实现，所以抛出：
MissingMethodException
为什么修完第一个又出现第二个
原调用链中其实有两层泛型 async：
PublishAsync<Scene, EntryEvent1>
    ↓
AEvent<Scene, EntryEvent1>.Handle
    ↓
具体事件 Run
一开始程序先死在 PublishAsync 状态机，所以看不到后面的问题。
移除 PublishAsync 的泛型状态机后，程序继续运行，随后又遇到：
AEvent<Scene, EntryEvent1>.<Handle>d__...::.ctor
说明 Handle 也存在完全相同的问题。因此两个方法都必须处理。
为什么不只用 link.xml 或 Preserve
link.xml 和 [Preserve] 主要解决“已有代码被裁剪”的问题。
这里更麻烦的是：IL2CPP 可能根本没有为特定泛型异步状态机生成对应的 AOT/Wasm 代码。保留元数据不等于生成具体泛型机器码，所以单纯增加 link.xml 不一定可靠。
而且状态机类型名类似：
<PublishAsync>d__4
它是编译器生成类型，方法稍有修改，编号就可能变化，手工维护也非常脆弱。
当前修复为什么有效
现在泛型方法不再使用 async：
public ETTask PublishAsync<S, T>(S scene, T a)
{
    // 收集任务
    return WaitAll(list);
}
真正的 await 放到非泛型方法：
private static async ETTask WaitAll(ListComponent<ETTask> list)
{
    await ETTaskHelper.WaitAll(list);
}
Handle 同样变成：
public ETTask Handle(S scene, A a)
{
    return EventSystem.HandleEvent(Run(scene, a));
}
由非泛型方法等待：
internal static async ETTask HandleEvent(ETTask task)
{
    await task;
}
现在编译器只需要生成：
WaitAll 状态机
HandleEvent 状态机
它们都没有 <S,T> 泛型参数，只需要生成一份确定的 AOT 实现，不再依赖：
<PublishAsync>d__<Scene, EntryEvent1>
<Handle>d__<Scene, EntryEvent1>
所以小游戏 IL2CPP 可以稳定调用。
一句话总结：
热更新代码调用了 AOT 程序集中的泛型 async 方法，但 IL2CPP 没有提前生成相应具体泛型异步状态机的 Wasm 代码；将泛型入口改为非 async，并把 await 下沉到非泛型方法后，消除了这类运行时缺失。

#### 3.2.1 开发规范：AOT 与热更新边界上的泛型异步方法

本项目统一采用以下规则：

> AOT 程序集中供热更新程序集调用的泛型公共方法，原则上不得直接声明为 `async`。泛型入口只负责参数处理和创建任务，实际的 `await` 应下沉到非泛型方法。

这不是说所有非热更新模块都绝对不能定义泛型 `async` 方法。真正危险的是以下条件同时存在：

1. 方法定义在 AOT 程序集中。
2. 方法是泛型方法，或者位于泛型类型中。
3. 方法使用 `async`，从而生成泛型异步状态机。
4. 方法由热更新程序集调用。
5. 具体泛型组合只在热更新代码中出现，IL2CPP 构建时无法完整预知。

尤其要注意包含值类型的泛型实参，例如事件参数通常是 `struct`。IL2CPP 对值类型泛型经常需要生成独立的具体实现，不能完全依赖引用类型泛型共享。

禁止使用的跨边界写法：

```csharp
// 位于 AOT 程序集，并供热更新代码调用。
public async ETTask PublishAsync<S, T>(S scene, T value)
    where S : class, IScene
    where T : struct
{
    ETTask task = CreateTask(scene, value);
    await task;
}
```

当热更新代码首次传入新的 `S`、`T` 组合时，上述代码可能依赖一个没有被 IL2CPP 生成的状态机：

```text
EventSystem.<PublishAsync>d__...<Scene, EntryEvent1>
```

推荐写法：

```csharp
// 泛型入口不是 async，不会生成带 S、T 的异步状态机。
public ETTask PublishAsync<S, T>(S scene, T value)
    where S : class, IScene
    where T : struct
{
    ETTask task = CreateTask(scene, value);
    return AwaitTask(task);
}

// 真正的 await 放在非泛型方法中。
private static async ETTask AwaitTask(ETTask task)
{
    await task;
}
```

如果泛型入口不需要额外的异常处理或资源释放，也可以直接返回已有任务：

```csharp
public ETTask Handle<T>(T value)
{
    return Process(value);
}
```

以下情况通常可以使用 `async`：

- 非泛型 AOT 方法。
- 完全位于热更新程序集中的方法。
- 不会被热更新代码引入新泛型组合的方法。
- 所有封闭泛型组合都已在 AOT 代码中显式引用，并经过目标平台真机构建验证的方法。

即使已经生成 `AOTGenericReferences.cs` 或配置 `link.xml`，也不能把它们视为这类代码必然安全的保证：

- `link.xml` 和 `[Preserve]` 主要防止已有类型和方法被裁剪。
- 它们不一定能让 IL2CPP 为所有编译器生成的泛型状态机产生具体 Wasm/AOT 代码。
- `<MethodName>d__...` 是编译器生成类型，名称和编号可能随源码变化，手工维护引用不稳定。

代码评审时，如果发现“AOT 泛型 API 被 Hotfix 调用”，应继续检查方法内部是否包含：

- `async` / `await`。
- `yield return` / `yield break`，它们会生成迭代器状态机。
- 捕获泛型参数或局部变量的 Lambda。
- 捕获泛型参数或局部变量的局部函数。

这些语法都可能生成隐藏的泛型类型。无法确认 IL2CPP 是否已生成具体实例时，优先改成“泛型同步入口 + 非泛型异步/迭代实现”，并在微信小游戏或其他 IL2CPP 目标上验证，而不能只以 Unity Editor 运行成功作为判断依据。

### 3.5 客户端 WebSocket 传输

涉及文件：

```text
Unity/Assets/Plugins/ETMiniGameWebSocket.jslib
Unity/Assets/Scripts/Core/Network/MiniGameNetworkSettings.cs
Unity/Assets/Scripts/Core/Network/MiniGameWebSocketTransport.cs
Unity/Assets/Scripts/Core/Network/KService.cs
Unity/Assets/Scripts/Hotfix/Share/Module/Message/NetComponentSystem.cs
Unity/Assets/Scripts/Hotfix/Client/Demo/NetClient/Main2NetClient_LoginHandler.cs
```

小游戏不能直接连接 ET 原有 UDP Router，因此增加了一层 WebSocket 传输适配：

1. `.jslib` 在 JavaScript/微信运行环境中创建原生 WebSocket。
2. 收发内容统一使用二进制帧。
3. C# 侧通过回调接收 WebSocket 数据。
4. `MiniGameWebSocketTransport` 实现 `IKcpTransport`。
5. `KService` 支持注入自定义 `IKcpTransport`。
6. 小游戏登录时选择 `NetworkProtocol.Websocket`，其他平台仍使用原来的 UDP。
7. ET 上层的 Router、KCP 包格式和 RPC 逻辑保持不变。

WebSocket 地址模板支持以下占位符：

```text
{0} = Router IP
{1} = Router 原端口
{2} = Router WebSocket 端口
```

当前模板：

```text
ws://{0}:{2}/et/
```

### 3.6 服务器 Router WebSocket

涉及文件：

```text
Unity/Assets/Scripts/Core/Network/WebSocketRouterTransport.cs
Unity/Assets/Scripts/Core/World/Module/Options/Options.cs
Unity/Assets/Scripts/Model/Server/Module/Router/RouterComponent.cs
Unity/Assets/Scripts/Hotfix/Server/Module/Router/RouterComponentSystem.cs
Unity/Assets/Scripts/Hotfix/Server/Demo/Watcher/WatcherHelper.cs
```

服务器新增两个命令行参数：

```text
--RouterWebSocket=1
--RouterWebSocketPortOffset=1000
```

当开关为 `1` 时，每个 Router 除原来的 UDP/TCP 监听外，还会启动一个 WebSocket 监听器。WebSocket 端口计算方式为：

```text
WebSocket端口 = Router原端口 + RouterWebSocketPortOffset
```

例如 Router 端口为 `30301`，偏移为 `1000`，对应 WebSocket 端口就是 `31301`。

使用端口偏移的原因是同一个端口不能同时由原 Router TCP/UDP 协议和 HTTP/WebSocket 监听器占用。偏移量本身没有协议含义，只要客户端、服务器、防火墙和反向代理配置一致即可。

`WatcherHelper` 会把这两个参数继续传给它启动的子进程，因此单进程和 Watcher 多进程启动方式都支持 WebSocket。

### 3.8 微信构建预检与 YooAsset 菜单

预检会验证：

- `GlobalConfig.CodeMode = Client`。

- Release 构建使用 HTTPS/WSS，而不是本地 IP、HTTP 或 WS。
- 微信转换 SDK 的 CDN 配置有效。

## 四、GlobalConfig 推荐配置

### 4.1 本机开发者工具联调

仅用于微信开发者工具或局域网调试：

```text
CodeMode = Client
EPlayMode = WebPlayMode
BuildType = Debug
ResourceHostServer = http://127.0.0.1:8080
ResourceFallbackHostServer = 留空
ResourceAppVersion = v1.0
MiniGameRouterHttpUrl = http://127.0.0.1:30300/get_router
MiniGameRouterWebSocketUrl = ws://{0}:{2}/et/
MiniGameRouterWebSocketPortOffset = 1000
```

使用 `Debug` 的原因是构建预检会允许本地 HTTP/WS 并给出警告。每次改变 `BuildType` 后，都应重新执行 F6、HybridCLR 生成和 YooAsset 构建，保证编译链模式一致。

### 4.2 正式发布

正式版本建议：

```text
BuildType = Release
EPlayMode = WebPlayMode
ResourceHostServer = https://资源合法域名
MiniGameRouterHttpUrl = https://接口合法域名/get_router
MiniGameRouterWebSocketUrl = wss://网关合法域名/et/
```

正式发布不应把 Router 内网 IP 和端口直接返回给客户端。建议由公网 WSS 网关或反向代理承接连接，再转发到内部 Router WebSocket 端口。

`BuildType = Release` 时，本项目的构建预检会直接拒绝 HTTP、WS、localhost 和回环地址。

## 五、完整导出流程

下面是首次出包或需要重建小游戏 Player 时的全量流程。修改 AOT/底层代码、切换 BuildType 或目标平台、更新 HybridCLR 或首包配置后使用此流程；只修改热更新代码或远端资源时，见第九节的增量流程。

### 第 1 步：切换微信小游戏目标

在 Unity Build Profiles/Build Settings 中切换到：

```text
Weixin MiniGame / MiniGame
```

等待 Unity 完成平台切换和脚本重新编译。

### 第 2 步：检查运行配置

检查 `Assets/Resources/GlobalConfig.asset`：

- `CodeMode = Client`
- `EPlayMode = WebPlayMode`
- 本地调试使用完整的 HTTP/WS 地址。
- 正式发布使用 HTTPS/WSS 合法域名。
- `ResourceAppVersion` 和实际 CDN 目录一致。

还要确认 Build Settings 中第一个启用场景是：

```text
Assets/Scenes/Init.unity
```

### 第 3 步：编译 ET 热更新代码

在 Unity 中按：

```text
F6
```

或者执行项目中对应的：

```text
ET -> Compile
```

该步骤生成当前 BuildType 和当前平台使用的热更新 DLL。
首次迁移到 `Unity/BuildArtifacts/HotUpdateDlls` 后需执行一次 F6；之后仅重启编辑器不会清理该目录，无需因此重复编译。

### 第 4 步：生成 HybridCLR 产物

依次执行：

```text
HybridCLR -> Generate -> All
HybridCLR -> CopyAotDlls
```

必须确认目标是 `MiniGame`。`CopyAotDlls` 后，以下两边的 DLL 内容应该一致：

```text
Unity/HybridCLRData/AssembliesPostIl2CppStrip/MiniGame
Unity/Assets/Bundles/AotDlls
```

如果报：

```text
Unity.ThirdParty.dll 缺失或已过期
```

表示裁剪后的源 DLL 与资源目录中的 `.bytes` 缺失或内容哈希不一致，不能仅凭这条报错断定是哪一侧缺失。先检查两边文件；源 DLL 缺失时重新执行 `Generate -> All`，然后执行 `CopyAotDlls`，再重新构建 YooAsset。

### 第 5 步：构建 YooAsset

执行：

```text
ET -> WeChat -> Build YooAsset Package
```

产物目录：

```text
Unity/Bundles/MiniGame/DefaultPackage/<构建版本>
```

菜单使用时间生成内部包版本，例如：

```text
2026-07-23-2316
```

这个内部包版本与对外 CDN 目录 `ResourceAppVersion = v1.0` 是两层概念：

- 内部包版本用于 YooAsset Manifest。
- `v1.0` 来自 `Unity/Assets/Resources/GlobalConfig.asset` 的 `ResourceAppVersion`，是部署目录名；修改它时，发布目录与客户端请求路径会一起变化。代码中的默认值定义在 `GlobalConfig.cs`，实际运行以资源配置为准。

### 第 6 步：发布 YooAsset 到 CDN

在 Unity 菜单执行：

```text
ET -> WeChat -> Publish YooAsset to Local CDN
```

菜单根据 `StreamingAssets/Bundles/DefaultPackage` 的版本文件选择当前 YooAsset 构建产物，将文件发布到：

```text
<微信 SDK 的 ProjectConf.relativeDST>/webgl/CDN/MiniGame/<ResourceAppVersion>
```

本地联调示例：

```text
Unity/WXBuild/webgl/CDN/MiniGame/v1.0
```

当前 `ProjectConf.relativeDST = WXBuild`，`ResourceAppVersion = v1.0`。菜单会先覆盖资源和 Manifest，最后更新 `.version` 文件。它只复制到本地微信导出工程，不会上传远程 CDN；正式发布仍需将该目录的内容上传至实际资源服务器。最终应该能通过浏览器或 curl 访问该目录中的 YooAsset 版本文件和 Manifest。

注意，微信转换 SDK 的主包数据 CDN 与 YooAsset CDN 是两组配置：

- `MiniGameConfig.ProjectConf.CDN`：加载转换后生成的 `.data` 等 Unity 主包文件。
- `GlobalConfig.ResourceHostServer`：加载 `CDN/MiniGame/v1.0` 下的 YooAsset 内容。

两者可以使用同一个域名，但目录和用途不同。

### 第 7 步：执行构建预检

执行：

```text
ET -> WeChat -> Validate Build
```

看到“微信小游戏构建预检通过”后再继续。

本地调试如果使用 HTTP/WS，`BuildType` 应为 `Debug`；正式 `Release` 必须先完成 HTTPS/WSS 配置。

### 第 8 步：生成并转换

这是微信 SDK 面板的“生成并转换”，对应 `WXConvertCore.DoExport()`：它会执行 MiniGame `BuildPlayer` 并转换到微信开发者工具工程。它不同于第 5 步的 YooAsset 资源包构建，也不同于微信开发者工具里的“编译”。

打开微信小游戏转换面板，检查：

```text
Development Build = 按当前 BuildType 选择
Auto Connect Profiler = 不需要时关闭
CDN = 与实际资源服务一致
输出目录 = Unity/WXBuild
```

正式构建建议：

```text
Development Build = 关闭
Auto Connect Profiler = 关闭
```

然后点击：

```text
生成并转换
```

转换完成后的微信开发者工具工程位于：

```text
Unity/WXBuild/minigame
```

完整导出可能重新生成 MiniGame 裁剪 AOT DLL。转换完成后再执行一次 `ET -> WeChat -> Validate Build`；若提示 AOT 元数据与源 DLL 不一致，依次执行 `HybridCLR -> CopyAotDlls`、`ET -> WeChat -> Build YooAsset Package`、`ET -> WeChat -> Publish YooAsset to Local CDN`，最后重新预检。此时不需要仅因此重复 F6 或重新转换 Player。

不要手工修改生成目录中的核心运行文件；下次转换会覆盖这些内容。需要长期保留的改动应放在 Unity 工程、转换模板或构建脚本中。

### 第 9 步：微信开发者工具重新编译

用微信开发者工具打开：

```text
Unity/WXBuild/minigame
```

资源、Wasm 或 Manifest 更新后，建议：

1. 清除全部缓存。
2. 删除可能残留的小游戏本地缓存。
3. 重新编译，快捷键通常为 `Ctrl+B`。

否则开发者工具可能继续请求旧哈希资源，表现为服务器文件已经更新，但客户端仍然访问旧文件。

## 六、本地资源服务器

本地调试可以从仓库根目录启动：

```powershell
python -m http.server 8080 --directory .\Unity\WXBuild\webgl
```

验证主包文件：

```powershell
curl.exe -I http://127.0.0.1:8080/<hash>.webgl.data.unityweb.bin.txt
```

验证 YooAsset 文件时，使用日志中显示的实际 URL：

```text
http://127.0.0.1:8080/CDN/MiniGame/v1.0/...
```

如果 curl 返回 `200`，但开发者工具仍显示 `503`：

- 确认 Python 服务没有重启或被其他进程占用。
- 清除微信开发者工具缓存。
- 确认 SDK CDN 配置没有指向旧地址。
- 确认请求的哈希文件确实位于服务根目录。
- 重新编译小游戏工程。

## 七、服务器启动与 WebSocket 配置

### 7.1 生成服务器配置

以 `Localhost` 启动配置为例，在：

```text
Unity/Assets/Config/Excel/StartConfig/Localhost/StartMachineConfig.xlsx
```

设置：

```text
OuterIP = 局域网 IP，例如 192.168.1.7
InnerIP = 127.0.0.1
```

然后执行项目原有的 Luban 配置生成流程。

如果 Router 返回的仍然是 `127.0.0.1`，小游戏会尝试连接它自己的回环地址，最终出现 `get router fail` 或 RPC `110307`。

### 7.2 手动编译服务器

在仓库根目录执行：

```powershell
dotnet build .\ET.sln
```

编译完成后确认 `Bin/App.dll` 已更新。新增命令行参数后如果没有重新编译，会报：

```text
Option 'RouterWebSocket' is unknown
Option 'RouterWebSocketPortOffset' is unknown
```

### 7.3 使用 ServerTools 启动

打开：

```text
ET -> ServerTools
```

选择：

```text
StartConfig = Localhost
起服模式 = Develop
Router WebSocket = 开启
WebSocket 端口偏移 = 1000
```

然后根据需要点击：

```text
Start Server (Single Process)
```

或：

```text
Start Watcher
```

### 7.4 命令行启动

```powershell
cd .\Bin

dotnet App.dll `
  --Process=1 `
  --AppType=Server `
  --StartConfig=StartConfig/Localhost `
  --Develop=1 `
  --Console=1 `
  --RouterWebSocket=1 `
  --RouterWebSocketPortOffset=1000
```

服务器日志中应该出现类似：

```text
Router WebSocket listener started: ws://0.0.0.0:31301/et/
```

### 7.5 Windows URLACL

服务器当前的 WebSocket 监听基于 `HttpListener`。Windows 即使端口没有被占用，也可能因为没有 URL 保留权限而报：

```text
HttpListenerException (5): 拒绝访问
```

使用管理员 PowerShell 执行：

```powershell
netsh http add urlacl url=http://+:31301/et/ user=Everyone
netsh http add urlacl url=http://+:31302/et/ user=Everyone
netsh http add urlacl url=http://+:31303/et/ user=Everyone
netsh http add urlacl url=http://+:31304/et/ user=Everyone
```

查看配置：

```powershell
netsh http show urlacl
```

URLACL 解决的是“服务器进程是否有权监听该 HTTP URL”，它和防火墙不是同一个配置。

### 7.6 Windows 防火墙

使用管理员 PowerShell 放行 Router WebSocket 端口：

```powershell
netsh advfirewall firewall add rule `
  name="ET Router WebSocket 31301-31304" `
  dir=in `
  action=allow `
  protocol=TCP `
  localport=31301-31304 `
  profile=private
```

还应按实际部署方式放行：

- `30300`：RouterManager HTTP。
- `8080`：本地资源 HTTP 服务。
- `31301-31304`：Router WebSocket。

正式服务器通常只对公网开放 HTTPS/WSS 网关端口，由反向代理访问内部 ET 端口。

## 八、常见问题

### 8.1 `still waiting runDependencies`

典型日志：

```text
still waiting runDependencies, ids=["wasm-preloadAssets"]
```

这不是根因，而是 Unity 主数据包没有下载完成。继续查它前面的 HTTP 状态码、CDN 地址和哈希文件。

### 8.2 `.webgl.data...txt` 返回 503

检查：

- `MiniGameConfig.ProjectConf.CDN` 是否正确。
- 文件是否在 `Unity/WXBuild/webgl` 服务根目录。
- 资源服务器是否能被开发者工具访问。
- 微信开发者工具是否缓存了旧 CDN 或旧哈希。

### 8.3 `Insecure connection not allowed`

本地测试将 Unity 的 `Allow downloads over HTTP` 设为 `Always Allowed`。

正式环境不要依赖该开关，应改成 HTTPS。

### 8.4 `Unity.ThirdParty.dll 缺失或已过期`

预检同时检查 `HybridCLRData/AssembliesPostIl2CppStrip/MiniGame` 中的源 DLL 和 `Assets/Bundles/AotDlls` 中的 `.bytes`，并比较哈希。这条报错可能是任一文件缺失，也可能是两边内容不一致。

本次联调的实际顺序是：完整导出的预检先报告 `Unity.ThirdParty.dll` 未通过一致性校验；Unity 随后仍执行 HybridCLR 的构建前回调，重建（清空）MiniGame 裁剪 AOT 目录；由于 Player 构建失败，没有完成生成并填回 DLL 的阶段。因此事后看到目录为空，不能反推它在首次预检前就为空，也不表示每次成功导出都会留下空目录。

如果源目录已空，按顺序恢复：

```text
HybridCLR -> Generate -> All
HybridCLR -> CopyAotDlls
ET -> WeChat -> Build YooAsset Package
ET -> WeChat -> Validate Build
```

如果源 DLL 仍在而只是 `.bytes` 过期，可先执行 `CopyAotDlls`、重建 YooAsset、发布到 CDN 并预检；如果 AOT 代码、目标平台或构建模式改变，则执行完整的 `Generate -> All`。预检通过后再重试“生成并转换”。成功转换也可能再次生成不同的源 DLL，按第 8 步的转换后预检处理。

### 8.5 `MissingMethodException ... async ... .ctor`

这是泛型异步状态机被 IL2CPP/HybridCLR 裁剪或未正确实例化。当前 EventSystem 相关问题已经通过“泛型入口非 async、非泛型方法负责 await”处理。

如果后续出现同类错误，优先检查报错方法是否同时满足：

- 泛型方法。
- 使用 `async`。
- 位于热更新程序集或跨 AOT/热更新边界调用。

### 8.6 登录错误 `110307`

`110307` 只是上层“获取或连接 Router 失败”的业务错误，继续查看内部异常。

重点检查：

- RouterManager 返回的是不是客户端可访问的 IP。
- 服务器是否带 `--RouterWebSocket=1` 启动。
- WebSocket 端口偏移是否与客户端一致。
- URLACL 是否已经配置。
- Windows 防火墙是否放行。
- 日志中是否出现 WebSocket listener started。

### 8.7 命令行参数 unknown

说明当前运行的 `Bin/App.dll` 仍是旧版本。先停止服务器，再重新执行：

```powershell
dotnet build .\ET.sln
```

然后确认启动的是本项目最新的 `Bin/App.dll`。

### 8.8 开发者工具持续等待 `wasm-instantiate` / `wasm-preloadAssets`

这两个名称表示启动依赖尚未完成，不能直接认定为网络故障。2026-10-20 红蓝 Demo 出现手机可运行、Windows 微信开发者工具卡住的情况；独立对照后，使用团结自带 Wasm 优化器对导出的原始 `.wasm` 执行 `-Oz --strip-debug`，再 Brotli 压缩、替换代码分包并同步 `game.js` 的 `CODE_FILE_MD5`，用户确认完整游戏可以进入场景。

仅移除调试名称未解决本次问题；优化并保留调试信息尚未测试。`--strip-debug` 会影响 Wasm 函数名调用栈和源码调试，但不关闭 `Debug.Log` 等日志。该处理目前是独立候选工程的导出后步骤，尚未自动接入一键构建，也不能据此确定开发者工具内部根因或通用文件大小上限。

命令、路径、大小变化、对照结果和回归边界详见 [RedBlue 实施与验证：2026-10-20 开发者工具 Wasm 初始化卡住的排查与处理](RedBlue_Demo实施与验证.md)。原始手机可运行工程应保留，优化包另行完成手机、玩法和性能回归。

## 九、推荐的日常增量流程

只修改 UI、Prefab 或普通资源时：

```text
1. ET -> WeChat -> Build YooAsset Package
2. ET -> WeChat -> Publish YooAsset to Local CDN
3. 微信开发者工具重新编译并验证资源
```

若改动的是首包内置资源、启动场景或 Player 配置，才需要重新“生成并转换”。开发者工具仍加载旧版本时，再清除缓存后编译。

修改热更新 C# 代码时：

```text
1. F6
2. ET -> WeChat -> Build YooAsset Package
3. ET -> WeChat -> Publish YooAsset to Local CDN
4. 微信开发者工具重新编译并验证热更
```

`Unity.Hotfix`、`Unity.HotfixView` 等热更 DLL 已通过资源包更新时，不必仅为这次改动重建 AOT 或完整导出 Player。若改动了 AOT/底层程序集、程序集引用、首包配置，或运行端无法仅靠资源更新取得新代码，则改走下面的全量流程；仍加载旧包时再清除开发者工具缓存。

修改 AOT、泛型、程序集引用、HybridCLR 配置或切换 BuildType/平台时：

```text
1. F6
2. HybridCLR -> Generate -> All
3. HybridCLR -> CopyAotDlls
4. ET -> WeChat -> Build YooAsset Package
5. ET -> WeChat -> Validate Build
6. ET -> WeChat -> Publish YooAsset to Local CDN
7. 生成并转换
8. 微信开发者工具编译并验证，必要时清缓存
```

修改服务器代码或命令行参数时：

```text
1. 停止旧服务器
2. dotnet build .\ET.sln
3. 使用 ServerTools 或完整命令行重新启动
4. 检查 Router WebSocket 监听日志
```

## 十、正式上线前仍需完成

当前局域网登录链路已经打通，但正式发布前还需要：

- 准备备案且已加入微信后台合法域名的 HTTPS 资源域名。
- 准备 HTTPS RouterManager 接口。
- 准备 WSS 网关或反向代理，并配置有效 TLS 证书。
- 不向客户端暴露内网 Router 地址。
- 设计 YooAsset 版本发布、回滚和 CDN 缓存刷新流程。
- 检查小游戏包体、首包资源和分包策略。
- 在真机上验证弱网、断线重连、切后台和网络切换。
- 评估所有原 Thread/ThreadPool Fiber 映射到主线程后的性能。
- 使用 `Release` 完成一次从 F6 到上传的全量构建验证。
