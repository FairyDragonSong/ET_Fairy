# 安卓构建流程原理

本文记录 YIUI 项目构建 Android 包时各个步骤的作用、执行原理、输入输出及相互关系。

当前完整流水线为：

```text
切换 Unity BuildTarget 到 Android
    ↓
F6 / ET → Compile
    ↓
HybridCLR → Generate → All
    ↓
HybridCLR → CopyAotDlls
    ↓
YooAsset ForceRebuild
    ↓
BuildPackage（BuildOptions = None）
```

本文目前记录前两部分：

1. `F6 / ET → Compile`
2. `HybridCLR → Generate → All` 与 `HybridCLR → CopyAotDlls`

---

## 一、F6 / ET → Compile

### 1. 核心作用

`F6` 和 Unity 菜单中的 `ET → Compile` 是同一个入口。

这一步不是生成 APK，也不是构建 YooAsset 资源包。它的核心任务是：

> 根据当前 Unity 平台、ET 的 CodeMode 和 BuildType，编译 4 个 ET 业务程序集，并将 DLL/PDB 转换成 Unity 可以作为资源处理的 `.bytes` 文件。

整体流程：

```text
刷新 Unity 资源
    ↓
根据 CodeMode 选择客户端/服务端代码
    ↓
根据 BuildType 设置开发或非开发编译选项
    ↓
针对当前 BuildTarget 编译 Unity Player 程序集
    ↓
取得 4 个 ET 业务 DLL 和 PDB
    ↓
复制为 .dll.bytes / .pdb.bytes
    ↓
刷新资源并同步 IDE 工程文件
```

### 2. 菜单入口

入口位于：

```text
Unity/Assets/Scripts/Editor/Assembly/AssemblyTool.cs
```

菜单定义为：

```text
ET/Compile _F6
```

因此点击 `ET → Compile` 和按下 `F6` 完全等价，都会进入同一个编译流程。

开始时会强制刷新 Unity 资源，避免以下情况导致编译出旧代码：

- Unity 关闭了 Auto Refresh；
- 代码刚由外部编辑器修改，Unity 尚未识别；
- 文件时间戳或资源数据库没有及时更新。

### 3. 根据 CodeMode 选择代码范围

编译前会读取：

```text
Unity/Assets/Resources/GlobalConfig.asset
```

其中 `CodeMode` 有三种：

| CodeMode | 含义 |
|---|---|
| Client | 只编译客户端需要的业务代码 |
| Server | 只编译服务端需要的业务代码 |
| ClientServer | 同时包含客户端和服务端代码 |

项目通过创建或删除各目录中的 `Ignore.asmdef`，控制某些目录是否归入目标业务程序集。

- 删除 `Ignore.asmdef`：目录中的代码重新归入父程序集，参与业务 DLL 编译；
- 恢复 `Ignore.asmdef`：目录被隔离，不进入目标业务 DLL。

当前 `GlobalConfig.asset` 中配置的是：

```text
CodeMode = Client
```

因此当前 F6 流程主要生成客户端运行所需的程序集内容，服务端专用代码会被隔离。

### 4. 根据 BuildType 设置编译选项

`BuildType` 分为：

| BuildType | 编译选项 |
|---|---|
| Debug | DevelopmentBuild |
| Release | None |

当前项目配置为：

```text
BuildType = Release
```

因此这次脚本编译不启用 DevelopmentBuild 选项。

需要注意：项目的热更 DLL 输出目录固定为：

```text
Unity/BuildArtifacts/HotUpdateDlls
```

该目录不随编辑器退出清理；实际编译模式仍以 BuildType 和编译选项为准，不能通过目录名称判断。

### 5. 针对当前 BuildTarget 编译

F6 使用 Unity 的 Player 脚本编译管线，而不是普通的 `dotnet build`。

它会根据 Unity 当前激活的平台进行编译，例如：

- Android；
- Windows 64 位；
- iOS；
- macOS。

因此编译过程会受到以下内容影响：

- 当前 BuildTarget；
- 平台条件编译宏；
- Unity Player 程序集引用；
- asmdef 依赖关系；
- API 兼容设置；
- DevelopmentBuild 编译选项。

正式构建 Android 包之前，应先把 Unity BuildTarget 切换到 Android，再执行 F6。否则生成的 DLL 可能使用了其他平台的编译条件。

### 6. `UNITY_COMPILE` 临时宏

F6 调用 Unity Player 编译管线时，会为本次编译临时增加：

```text
UNITY_COMPILE
```

它只对这一次脚本编译有效，不会永久写入 Unity 的 Scripting Define Symbols。

4 个业务程序集的 asmdef 都具有类似约束：

```text
UNITY_COMPILE || UNITY_EDITOR
```

含义是只要满足以下任意条件，程序集就可以参与编译：

- 当前在 Unity Editor 环境中；
- 当前是 F6 发起的 Player 脚本编译，并临时定义了 `UNITY_COMPILE`。

因此，在 Player 编译环境中即使没有 `UNITY_EDITOR`，F6 仍能明确地让这些业务程序集参与编译。

### 7. 生成的业务程序集

F6 最终关注以下 4 个程序集：

| 程序集 | 主要职责 |
|---|---|
| Unity.Model | 数据模型、组件定义、协议对象及基础业务结构 |
| Unity.ModelView | 与 Unity 表现层相关的模型和组件 |
| Unity.Hotfix | 可热更新的业务逻辑 |
| Unity.HotfixView | 可热更新的客户端表现和 UI 逻辑 |

它们的大致依赖关系为：

```text
Unity.Model
   ├── Unity.ModelView
   └── Unity.Hotfix
           └── Unity.HotfixView

Unity.ModelView ─────────┘
```

编译中间产物位于：

```text
Unity/BuildArtifacts/HotUpdateDlls
```

### 8. 复制为 Unity 资源

编译成功后，流程会先清理：

```text
Unity/Assets/Bundles/Code
```

然后将 4 组 DLL/PDB 复制并改名：

```text
BuildArtifacts/HotUpdateDlls/Unity.Hotfix.dll
    ↓
Assets/Bundles/Code/Unity.Hotfix.dll.bytes
```

```text
BuildArtifacts/HotUpdateDlls/Unity.Hotfix.pdb
    ↓
Assets/Bundles/Code/Unity.Hotfix.pdb.bytes
```

最终主要生成：

```text
Unity.Model.dll.bytes
Unity.Model.pdb.bytes
Unity.ModelView.dll.bytes
Unity.ModelView.pdb.bytes
Unity.Hotfix.dll.bytes
Unity.Hotfix.pdb.bytes
Unity.HotfixView.dll.bytes
Unity.HotfixView.pdb.bytes
```

`.dll` 改成 `.dll.bytes` 后，Unity 不会把它当作普通托管插件直接载入，而会把它作为二进制资源处理。这样这些文件可以：

- 被 YooAsset 收集和构建；
- 作为资源下载和更新；
- 在运行时读取字节数组；
- 通过 `Assembly.Load` 动态加载。

`.pdb.bytes` 是调试符号，可用于提供更完整的异常堆栈、源文件名和代码行号。

### 9. 运行时用途

当前项目启用了：

```text
EnableDll = true
```

在 Unity Editor 中运行时，项目会直接读取 `Assets/Bundles/Code` 中的 DLL/PDB 字节并动态加载。

在真正的 Android 包中，这些文件会先由 YooAsset 作为资源加载，再交给程序集加载逻辑。

因此，如果业务代码已经修改但没有重新执行 F6，后续 YooAsset 很可能仍会把旧 DLL 构建进资源包。

### 10. 本步骤不负责的内容

F6 不负责：

- 生成 HybridCLR 方法桥接代码；
- 生成 AOT 泛型引用；
- 生成或复制裁剪后的 AOT DLL；
- 构建 YooAsset 资源包；
- 生成最终 APK。

一句话总结：

> F6 根据当前平台和 ET 配置生成最新的 4 个业务 DLL，并把它们转换为后续 YooAsset 和 HybridCLR 可以加载的 `.bytes` 资源。

## 二、HybridCLR → Generate → All 与 CopyAotDlls

## 1. HybridCLR 是什么

HybridCLR 为 Unity IL2CPP 运行环境增加了运行新 C# DLL 的能力，使 Android/iOS 等 IL2CPP 平台可以实现代码热更新。

### Mono 与 IL2CPP 的差异

Mono 的基本流程：

```text
C# → DLL → Mono 虚拟机执行
```

Mono 可以在运行时读取并执行 DLL，因此天然比较适合代码热更新。

IL2CPP 的基本流程：

```text
C# → DLL → C++ → 原生机器码 → APK/应用
```

IL2CPP 使用 AOT（Ahead Of Time，提前编译）。应用发布后，新下载的 C# DLL 没有经历构建期间的 C++ 和原生代码转换，因此普通 IL2CPP 无法完整执行它。

HybridCLR 在 IL2CPP 中加入解释执行能力，使运行方式变为：

```text
首包稳定代码
    ↓
IL2CPP 提前编译为原生机器码执行

热更新 DLL
    ↓
HybridCLR 解释执行
```

“Hybrid”表示两种方式混合运行：

- 首包固定代码由 IL2CPP AOT 原生执行；
- 后续热更新 DLL 由 HybridCLR 解释执行；
- 两边通过生成的桥接代码互相调用。

## 2. Generate → All 的核心作用

`HybridCLR → Generate → All` 的作用是：

> 根据当前平台、当前热更新 DLL 和当前项目程序集，生成正式 IL2CPP 构建及运行热更新所需的全部辅助数据。

它不是最终 APK 构建，但会执行一套较重的打包前准备流程：

```text
准备热更新 DLL
    ↓
生成 IL2CPP 定义
    ↓
生成防裁剪配置
    ↓
临时构建并取得裁剪后的 AOT DLL
    ↓
生成方法桥接和反向 P/Invoke 包装
    ↓
生成 AOT 泛型引用信息
```

## 3. 准备并分析热更新 DLL

当前项目配置的热更新程序集为：

```text
Unity.Model
Unity.Hotfix
Unity.ModelView
Unity.HotfixView
```

项目还将下面的目录配置为外部热更新 DLL 来源：

```text
BuildArtifacts/HotUpdateDlls
```

它与前面 F6 的中间输出目录对应。

两步之间的关系可理解为：

```text
F6
  生成最新的 ET 业务 DLL
          ↓
Generate All
  分析这些 DLL，生成 IL2CPP/HybridCLR 配套数据
```

HybridCLR 会分析：

- 热更新代码包含哪些类型和方法；
- 热更新代码引用了哪些 AOT 类型；
- 使用了哪些泛型组合；
- 存在哪些解释器与原生代码之间的调用。

## 4. 生成 IL2CPP 定义

HybridCLR 会根据当前 Unity 版本、IL2CPP 版本、构建平台和项目程序集生成相应的适配数据。

这些信息用于说明：

- 当前 IL2CPP 的结构和环境；
- HybridCLR 解释器如何接入 IL2CPP；
- 类型和方法如何对应；
- 后续桥接代码与运行时数据应如何生成。

## 5. 生成 link.xml，防止代码被裁剪

IL2CPP 构建会进行代码裁剪。如果 Unity 判断某些类型或方法没有被使用，可能会把它们从最终包中删除。

热更新 DLL 是运行时才加载的，Unity 构建期间不一定能看到热更新代码对首包代码的调用关系。

可能出现：

```text
热更新 DLL 需要某个 AOT 方法
    ↓
Unity 构建期间看不到这次调用
    ↓
该方法被当成无用代码裁剪
    ↓
真机运行热更新代码时调用失败
```

Generate All 会分析热更新 DLL 对 AOT 程序集的引用并生成 `link.xml`，告诉 Unity 哪些类型和方法需要保留。

## 6. 生成裁剪后的 AOT DLL

Generate All 会针对当前 BuildTarget 做一次临时 IL2CPP 构建。对于 Android，产物主要位于：

```text
Unity/HybridCLRData/AssembliesPostIl2CppStrip/Android
```

这里得到的是经过当前平台、当前配置和 Unity 裁剪流程处理后的 AOT DLL。

HybridCLR 必须以最终裁剪结果为依据，才能正确分析：

- 最终包中实际还保留了哪些类型和方法；
- 哪些泛型代码和元数据仍然存在；
- 需要生成哪些调用桥接；
- 需要补充哪些 AOT 元数据。

可以把这一步理解为：

> HybridCLR 先模拟一次构建，确认最终 Android 包中的 AOT 代码世界实际是什么样子。

## 7. 生成方法桥接代码

热更新代码由解释器执行，首包代码由 IL2CPP 原生执行，两者的方法调用格式并不完全相同。

当出现以下调用时，需要桥接层：

- 热更新代码调用 AOT 方法；
- AOT 代码回调热更新方法；
- 热更新代码调用 AOT 泛型方法；
- 原生代码触发热更新委托；
- 反向 P/Invoke 调用。

桥接层负责：

- 转换参数和返回值；
- 处理引用类型和值类型；
- 连接解释器函数与原生函数；
- 处理委托、泛型和反向调用。

流程可以理解为：

```text
HybridCLR 热更新解释器
    ↓ 解释器调用格式
方法桥接层
    ↓ IL2CPP 原生调用格式
AOT 原生代码
```

如果新增了跨解释器/AOT 边界的方法签名却没有重新生成，正式包中可能缺少所需桥接函数。

## 8. 生成 AOT 泛型引用

IL2CPP 需要在构建时提前知道需要生成哪些泛型实例，例如：

```text
List<Player>
Dictionary<long, Player>
SomeMethod<MyStruct>()
```

某些泛型组合可能只出现在未来加载的热更新 DLL 中，首包代码没有直接使用。普通 IL2CPP 在构建时就可能没有生成或保留相应内容。

Generate All 会分析热更新 DLL 使用的 AOT 泛型，生成泛型引用信息，帮助 IL2CPP 在正式构建时保留或生成需要的泛型代码与元数据。

## 9. Generate All 的主要产物

### 项目内的生成配置和代码

```text
link.xml
AOTGenericReferences.cs
方法桥接代码
反向 P/Invoke 包装代码
IL2CPP 相关定义
```

这些文件会参与之后的正式 IL2CPP 构建。

### HybridCLR 中间数据

```text
HybridCLRData/HotUpdateDlls/Android
HybridCLRData/AssembliesPostIl2CppStrip/Android
HybridCLRData/StrippedAOTDllsTempProj/Android
```

它们包含：

- 热更新 DLL 的构建或分析副本；
- 裁剪后的 AOT DLL；
- 临时 IL2CPP 构建工程；
- 代码生成所需的中间数据。

## 10. CopyAotDlls 的核心作用

`HybridCLR → CopyAotDlls` 的作用是：

> 从 Generate All 产生的裁剪后 AOT DLL 中，挑选项目配置的 DLL，复制到 YooAsset 资源目录并改名为 `.bytes`。

Android 下的流程：

```text
HybridCLRData/AssembliesPostIl2CppStrip/Android
    ↓
选择 patchAOTAssemblies 中配置的 DLL
    ↓
Assets/Bundles/AotDlls
    ↓
将 .dll 改名为 .dll.bytes
```

执行时会先清理旧的：

```text
Unity/Assets/Bundles/AotDlls
```

再复制当前平台最新生成的 AOT DLL。

## 11. 当前项目复制的 AOT DLL

当前项目配置了以下 AOT 元数据程序集：

```text
Unity.ThirdParty.dll
Unity.Loader.dll
Unity.Core.dll
MongoDB.Bson.dll
CommandLine.dll
NLog.dll
System.dll
System.Core.dll
mscorlib.dll
MemoryPack.dll
System.Runtime.CompilerServices.Unsafe.dll
YIUIFramework.dll
Sirenix.Serialization.AOTGenerated.dll
```

复制后变为：

```text
Unity.ThirdParty.dll.bytes
Unity.Loader.dll.bytes
Unity.Core.dll.bytes
...
mscorlib.dll.bytes
```

目标目录为：

```text
Unity/Assets/Bundles/AotDlls
```

随后 YooAsset 会将它们作为资源进行收集和构建。

## 12. AOT DLL 为什么要作为资源放进包中

这些 AOT DLL 不是用于重新执行其中的代码。

AOT 程序集的代码已经由 IL2CPP 转换为原生机器码，存在 APK 的原生库中。复制进 `AotDlls` 的 DLL 主要用于提供完整元数据。

元数据包括：

- 类型定义；
- 方法定义；
- 字段信息；
- 方法签名；
- 泛型信息；
- 类型之间的关系。

可以这样理解：

```text
APK 中的原生库
    = 真正执行的 AOT 机器码

AotDlls/*.dll.bytes
    = 描述这些代码和类型结构的说明书
```

运行时，HybridCLR 会读取这些 `.dll.bytes`，通过 AOT 元数据补充接口将完整元数据加载进运行环境。

它主要用于支持：

- 热更新代码访问 AOT 类型；
- AOT 泛型实例；
- 泛型共享；
- 反射；
- 被裁剪或不完整的类型与方法元数据。

## 13. Generate All 与 CopyAotDlls 的关系

```text
HybridCLR → Generate → All
    │
    ├─ 分析热更新 DLL
    ├─ 生成防裁剪配置
    ├─ 生成桥接代码
    ├─ 生成泛型引用
    └─ 生成裁剪后的 AOT DLL
                    ↓
HybridCLR → CopyAotDlls
    │
    └─ 将指定的裁剪后 AOT DLL
       复制为 Assets/Bundles/AotDlls/*.bytes
                    ↓
YooAsset ForceRebuild
    │
    └─ 将热更新 DLL、AOT 元数据和其他资源构建成资源包
                    ↓
最终 Android 包运行
    │
    ├─ 加载 AOT 补充元数据
    └─ 加载并执行热更新 DLL
```

必须先执行 `Generate All`，再执行 `CopyAotDlls`。否则复制的可能是：

- 上一次生成的旧 AOT DLL；
- 其他平台生成的 DLL；
- 与当前裁剪和构建配置不一致的 DLL；
- 尚未生成的文件。

## 14. 平台一致性

Generate All 和 CopyAotDlls 都依据 Unity 当前激活的 BuildTarget。

构建 Android 时必须保证：

```text
Unity BuildTarget = Android
    ↓
F6 / ET → Compile
    ↓
HybridCLR → Generate → All
    ↓
HybridCLR → CopyAotDlls
    ↓
YooAsset ForceRebuild
    ↓
Android BuildPackage
```

不能在 Windows BuildTarget 下执行 Generate All，然后直接使用这套数据构建 Android。不同平台的条件宏、程序集、裁剪结果、IL2CPP 数据、桥接代码需求和 AOT DLL 都可能不同。

## 15. 前两部分的职责对照

| 步骤 | 主要职责 |
|---|---|
| F6 / ET → Compile | 生成最新的 ET 热更新业务 DLL |
| HybridCLR → Generate → All | 根据热更新 DLL 和当前 AOT 环境生成 HybridCLR 配套数据 |
| HybridCLR → CopyAotDlls | 将运行时需要的 AOT 元数据 DLL 复制进资源目录 |
| YooAsset ForceRebuild | 将热更新 DLL、AOT 元数据和其他资源构建成资源包 |
| BuildPackage | 构建最终 APK/应用 |

最简单的记法：

```text
F6
    生产最新的热更新代码

Generate All
    让 IL2CPP 准备好执行这些热更新代码

CopyAotDlls
    把运行时需要的 AOT“类型说明书”放进资源目录
```

正式出包前，以下情况应重新执行 `Generate All → CopyAotDlls`：

- 切换目标平台；
- 构建新的完整首包；
- Unity 或 HybridCLR 版本发生变化；
- AOT 程序集或其代码发生变化；
- 裁剪配置发生变化；
- 新增泛型组合；
- 新增热更新与 AOT 之间的调用签名；
- Development/Release 等构建配置发生变化。
